# Explanation-driven improvement

## Explain first and preserve the return point

An unclear term, “I did not understand”, “what does this module mean?” or a request to explain again is feedback about the current explanation. It is not proof that code, a Skill or a specification is wrong. This loop can run during ordinary work, Grill, Create, Replan or close.

1. Identify the original question and pending work/choice/version. Inspect the relevant source, current specification and owning capability's `knowledges/INDEX.md`; read the relevant entry. Keep current facts, intended behavior and hypotheses separate.
2. Explain the confusing distinction through the same concrete input or state transition. Define the roles, show why the result follows, then reconnect it to the full relevant architecture. Correct discoverable facts yourself.
3. If different interpretations would materially change the explanation or desired behavior, ask a focused Grill question after showing the alternatives. Do not ask a compulsory comprehension quiz or manufacture an unanswered preference. “I understand” is not Create/Replan/close approval.
4. Capture the actual words/source and bounded improvement question in the existing topic through `harness.observe` with `OwnerDraftId` and `OwnerScope` when known. Otherwise let Harness create a bounded topic. A Harness-upgrade subject uses ordinary draft modes; it is not a new draft type or Skill. Mark the cause unproven until evidence distinguishes it.
5. Resume the preserved work or actual pending question. During active Grill, apply its continuing-round rule. An explanation-only revision keeps the same candidate Gate; changed material content requires a new preview and actual decision. Feedback capture alone never creates a Change or blocks unrelated authorized work.

## Classify before selecting changes

| Evidence | Improvement owner and next action |
| --- | --- |
| Source and contract agree; this answer omitted a needed concept or example | Improve this explanation now. Retain a possible method gap; a general Skill edit needs selected scope, not just unfamiliarity. |
| The intended observable behavior is ambiguous or contradicts accepted expectations | Explain the current implementation and alternatives; Grill the desired contract. Route invalidated accepted planning through Replan. Do not silently repair a spec to match code. |
| Verified reusable fact is absent from owning knowledge | Propose or publish a concise factual article under existing authority, using source/current contract/example evidence. |
| A relevant current entry exists but was not read or used | Read and apply it, retain retrieval feedback, and avoid a duplicate article. |
| Source, spec and article disagree or facts are missing | Show the disagreement and a concrete check; retain an unproven question. Diagnosis and behavior repair follow their owning workflow. |
| The reader only needed a new term explained; no reusable deficiency is established | Provide that explanation. Record the signal without claiming a prompt defect or selecting repair. |

Several owners may apply. Record evidence for each instead of forcing one diagnosis.

## Publish only what the evidence and authority support

- Existing explicit authority can cover factual knowledge improvements; do not demand another permission or a new Change for an already selected bounded addition. Source, current contract and a representative example can admit factual documentation without fabricating a behavior RED/GREEN failure. Follow [knowledge admission](../../openspec/references/knowledge.md).
- Without authority to edit the proposed owner, keep the candidate and source in the topic draft and present it with the next useful improvement batch. Capturing feedback is not permission to edit unrelated Skills, specs or tools. User-directed “keep this idea; do not change behavior” supports a draft record, not a new behavior decision.
- Use [Harness evolution](../../harness/references/evolution.md) for source-aware selection and resolution. A selected factual addition records its source check, indexed target and result. A selected behavior repair retains its appropriate regression proof. Unselected or uncertain work stays pending/deferred; archive is not resolution.
- A later explanation must actually read the updated owning INDEX and relevant entry, check applicability against source/current contract, and use the useful model in the answer. Merely writing “knowledge reused” or finding a filename is not evidence of reuse.
- Preserve archived originals, omit transient machine paths from capability articles, and retain concise provenance. Keep the current topic's return point and unresolved sibling scopes when explicitly archiving a draft.
