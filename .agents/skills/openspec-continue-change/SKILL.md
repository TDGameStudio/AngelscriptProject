# Continue a Change

1. Use the explicit Change or resolve the canonical active Change in the selected workspace. The Change already exists: a new feature, architecture refactor, or major behavior change was created by [`openspec-create-change`](../openspec-create-change/SKILL.md) from an approved draft, so read `attachments/drafts/handoff.md` and `attachments/INDEX.md` as the accepted decision-complete input. Never reopen [`brainstorming`](../brainstorming/SKILL.md) `design` mode for this Change's scope after creation; route corrections to existing planning truth through `openspec-update-change`. Clear fixes and mechanical documentation work may have skipped the pre-creation gate; state that assumption in the proposal.
2. Call `openspec.status --change <id> --json` and select one missing artifact. Proposal and tasks are required; specs exist only for durable behavior; design exists only for non-obvious decisions.
3. Call `openspec.instructions <artifact> --change <id> --json`. Re-read its concrete context files. Apply context/rules as constraints, never copied prose.
4. Write one artifact to `writePath`; for a glob choose a concrete path permitted by `outputPattern`. Use the matching record/task reference from the `openspec` skill. When the selected artifact is `specs`, load the [Specification and Scenario Card contract](../openspec/references/specs.md), create deltas only for durable behavior, and actively evaluate every new or modified behavior clause. Prefer the useful information in a clause-owned detail block—including prose, lists, examples, or tables—beneath the exact clause and preserve it in the complete Scenario Card; omit a form when it adds no durable information and never add empty scaffolding.
5. Lift settled truth from the seeded attachments into the artifact you are writing: the `Exploration Carryover` and `attachments/drafts/design.md` feed proposal, specs, design, and tasks; the indexed `attachments/talks/` and `attachments/knowledges/` were already materialized by `openspec-create-change` per the [attachment contract](../openspec/references/attachments.md) and [knowledge contract](../openspec/references/knowledge.md) and are not recreated here. If planning uncovers a new non-obvious decision, add one indexed talk in the same edit; never paste the draft `log.md` or round state into the Change. This does not relax the one-workflow-artifact step.
6. Run strict change validation and report the next ready artifact.

When writing tasks, use the [Task authoring contract and semantic authoring check](../openspec/references/tasks.md) as the detailed authority, not just the template's heading syntax. List every new public name a task introduces in its **Interfaces**, taking settled names from the draft `glossary.md` (linked from `attachments/drafts/handoff.md`); grill any name not yet settled per [naming.md](../brainstorming/references/naming.md) before writing the task. Before reporting a plan as ready, run the plan-acceptance preflight: the header sections (`## Goal`, `## Architecture`, `## Global constraints`, `## Requirement coverage`) exist; every card carries the labels for its kind in order; every behavior card has at least one case tagged `new RED` and an Interfaces code fence when it names a symbol; every case opens with a header line matching the grammar in the [case catalog](../openspec/references/cases.md), every role or kind word outside the standard set is defined in that block's `Roles:` / `Kinds:` paragraph, every `deferred RED until X.Y` names a task present in `task_graph`, and tables appear only inside an `example-table` case; no forbidden phrase appears; `attachments/data/planning-validation.md` records the three-item self-review and is indexed. A plan failing preflight is not ready; repair it through `openspec-update-change`. The [draft contract](../brainstorming/references/drafts.md) explains what remains in the draft and is never copied. Follow real interfaces and cases through to their proving selection, including the baseline of final validation targets. Use the [verification policy](../harness/references/verification.md) for grouped RED/GREEN and shared runs. Strict structural validation alone does not prove the task is ready for a zero-context implementer.

```text
status -> instructions -> one concrete artifact -> strict validate
```

Fast-forward through all missing planning artifacts only when implementation was requested or an unattended continuation already carries an approved objective and decision-complete handoff. During unattended continuation, settle in-scope technical choices autonomously; a missing user-owned decision means the handoff was not decision-complete, so stop and report rather than inventing it. Do not hand-create manifest files, write implementation code, or replace existing artifacts in this skill.

Rich Markdown ownership is part of the authoring contract: direct Task and behavior-clause detail uses four spaces, nested blocks keep their own container, and useful information may be extensive. Preserve complete clauses with their headings, code, tables, lists, quotes, links and images; never flatten a card to its main sentence. Judge literal cases, actual interfaces and observable acceptance decisions, not section presence or word count.
