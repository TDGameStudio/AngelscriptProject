# Independent lifecycle consumer audit

These are isolated simulated host exercises, not actual project approvals or
proof that a selectable window rendered. Production lifecycle/Git mutation is
proved separately by the real temporary-repository fixtures in tasks.md.

## Method and provenance

- The system skill-creator independent forward-testing method supplies the
  evaluation boundary. Separate consumers receive raw requests, minimum facts
  and Skill instructions, without the author's intended response or other
  consumers' reports. They cannot change production files or call real user
  question tools. Their scratch output is under Saved/AgentTemp/lifecycle-consumers.
- The host adapter actually records submitted question payloads and returns
  pending/rendered-unknown; it rejects approval via optional-only
  request_user_input. Adapter acceptance is not real UI display or user consent.
- A fixed before-skills Markdown snapshot prevents later production edits from
  changing the baseline between turns. Both discussion arms receive the same
  raw requests and facts, with only evaluation-source identifiers changed.
- Raw conversations may retain Chinese because these are original test outputs,
  not replacement English planning. No simulated source authorizes live work.

## Observed baseline

- `consumer-before-discussion.txt`: four sequential user turns. The consumer
  submitted the initial preference form, processed the actual batch answer and
  side question, explained the plugin pointer, then submitted the next choice.
  It accepted the next textual answer, used a visible final-text question when
  the form was reported invisible, and obeyed explicit pause without suggesting
  creation. The historic premature-stop failure did not reproduce here.
- `consumer-before-explanation.txt`: two sequential turns. The consumer correctly
  explained implementation commit versus archive move versus canonical commit
  from current source. It did not read a capability knowledge INDEX in the first
  explanation. After an explicit request to retain the improvement, it inspected
  the core knowledge INDEX and wrote a separate scratch observation JSON, rather
  than a topic draft. No production behavior/Skill/spec changed.
- The explanation baseline also reports an overly broad Reference search and
  truncated external-source output, then a narrower source search. Those
  discarded results are not supporting evidence for its answer.

## Observed discussion and Gate behavior after editing

- `consumer-after-discussion.txt`: same four raw requests as the baseline. The
  consumer submitted two actual optional-clarification questions, processed the
  answer with a side question, re-explained repository pointers and mixed-file
  selection, used a visible textual fallback after the invisible-form report,
  and obeyed the final explicit pause without proposing creation. Both arms
  continued correctly; this pair does not demonstrate a reliability increase.
- `consumer-after-gates.txt`: separate Create/Replan/Close branches submitted
  actual simulated async approval questions. The adapter returned pending and
  unknown rendering. Additional explanation retained unchanged candidates and
  the same pending question. Cancelled/preselected forms did not become consent;
  the consumer used visible fallback questions. Actual pause retained each
  return point. The async-unavailable branch avoided the approval-prohibited
  optional tool; the adapter's rejection contract is not a live host rejection.
- An empty Grill frontier triggered coverage inspection and an open feedback
  state, without an invented choice or inferred convergence. These are single
  bounded traces, not a statistical sample or proof of real user comprehension.
- The Gate fixture lacks actual branch/patch/context/session/convergence data
  and some command/message details. The consumer explicitly left those unknown;
  none of the simulated questions is a production-ready authorization receipt.

## Structural proof and limits

`Protocol.Tests.ps1 -ActiveChange harness/feature-lifecycle-git-closure` passed
after the guidance edits. This verifies routing links and record contracts,
not explanation quality. The default repository-wide active-issue audit fails
four missing-proof fields in the unrelated existing
`angelscript/refactor-builder-source-entry` issue
`issue-20260913-105100-shared-source-makes-emit-real.md`. Replaying the HEAD
Protocol implementation reproduced those same four failures. The scoped

## Observed explanation and knowledge behavior

- `consumer-after-explanation.txt`: the first consumer response actually read
  the Git capability INDEX and lifecycle-checkpoints article, then checked
  ChangeClosure, closure_status and queue/execution source. It explained code
  commit versus directory move versus canonical-record commit, kept the given
  partial-close return point and retained the actual signal in an isolated
  topic README/CONTEXT/scoped design. It neither asked a comprehension quiz nor
  called unfamiliarity a proven Skill defect.
- The second actual user turn requested retaining the useful explanation,
  without changing behavior. The consumer reread current evidence and the same
  existing article; it retained a bounded example/table improvement candidate
  in that owner rather than publishing or duplicating knowledge. This differs
  from the baseline's separate scratch observation JSON. These two explanation
  arms are qualitative scenario comparisons, not a randomized reliability test.
- During its first read, the consumer found a real old core scenario that still
  implied advancing without the primary commit. The main task's later semantic
  sync replaced that named clause under the already accepted persistence scope.
  On rereading, the consumer correctly identified the changed current source,
  retained its earlier observation as historical and did not claim to have
  repaired it. This temporal boundary is explicit in the raw trace.
- The raw responses are retained as text attachments: original-language source
  and temporary links are historical evidence, not maintained English planning
  or promised live Change-local Markdown dependencies. The English audit owns
  conclusions and limitations; no simulated answer is production authority.

- `consumer-knowledge-fixture.txt` and `consumer-knowledge-cases.txt` retain
  seven independent raw requests plus a separately supplied later reuse round.
  The consumer explained a method gap, submitted actual questions for ambiguous
  understanding and ambiguous intended behavior, reused existing knowledge,
  retained contradictory/unselected claims and respected explicit no-edit scope.
  Only the authorized factual-publication branch wrote an isolated article and
  one INDEX entry (`consumer-knowledge-artifacts.json`); no code failure or extra
  approval was fabricated. All branches retained original topic return points.
- In the later round, the consumer actually reread that published INDEX/article
  and the source/contract, and used them to derive the supplied state. It did not
  invent a recovery API or idempotency absent from the synthetic source. This
  proves later-turn reuse by the same consumer, not fresh-context retention.
- There were eight actual explanation notes and two actual clarification forms
  in this synthetic branch exercise. Both forms remain pending/rendered unknown.
  A Windows stdin encoding failure happened before event delivery; the caller
  corrected it with Python UTF-8 mode and retained that limitation in the trace.

No live popup rendering, user approval, production publication or numerical
reliability claim is inferred from these consumer exercises. Runtime persistence
and feedback serialization are separately proved by real isolated route tests.
