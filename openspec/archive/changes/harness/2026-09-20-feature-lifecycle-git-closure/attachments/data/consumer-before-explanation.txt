本记录只解释给定的隔离 fixture，不代表当前真实项目的执行状态。没有查询、推进或修复真实队列，没有读取任何 active Change planning 或其他评估报告。

## 面向模拟用户的说明

我刚才把“Change 已归档”说得太笼统了。这个场景的准确状态是：**插件的实现已经保存为插件仓库中的提交，Change 记录也已经移入归档目录，但规范记录仓库的最终提交失败，所以整次收束尚未完成。** `Stage=archived` 和 `Complete=false` 分别描述这两件事，二者并不矛盾。

这里有两个仓库角色。插件仓库保存插件的代码版本；规范记录仓库由 `OpenSpecRoot` 指向，保存项目共用的 OpenSpec 记录。即使它们的文件看起来处于同一项目目录下，它们的 Git 提交仍然是分别完成的。一次插件提交不会同时把父仓库里的 Change 记录也提交。

**“实现”回答的是插件具体改成了什么；“归档记录”回答的是这项 Change 做了什么、依据什么验证、以什么结果结束。** 后者包含 Change 的设计和任务等记录、证据、结束结果，以及收束流程生成的回执。回执还会记下前面完成的实现提交，以便将记录和代码版本对应起来。

用同一个 Change 看这次发生的三个动作，区别就清楚了：

| 动作 | 它实际保存或改变的东西 | 给定场景中的结果 |
|---|---|---|
| 提交插件实现 | 把本次选中的插件代码改动保存到插件仓库的 Git 历史 | 已成功，插件提交存在 |
| 归档 Change 记录 | 将活动 Change 的记录移入归档目录，写入结束结果，并核验归档内容 | 已完成，归档目录存在，`Stage=archived` |
| 提交最终规范记录 | 把这次归档变化及已选定的相关记录保存到规范记录仓库的 Git 历史 | `pre-commit` 拒绝，最终提交不存在，`Complete=false` |

表里的第三步很关键：**文件已移动到归档目录，是工作目录里发生的变化；Git 最终提交成功，才证明这些变化已经进入规范记录仓库的历史。** “目录存在”和“已经提交”是两个可以分别检查的事实。给定场景恰好完成了前一个事实，还没完成后一个。

从实际代码看，`harness.change.close` 调用 `Close-HarnessChange`，由它顺序完成插件提交、记录整理、归档和最终记录提交。下面是当前代码中与这个问题有关的顺序；中间的准备、撤回分支和校验细节省略，箭头表示必须依次完成的步骤：

```text
harness.change.close → Close-HarnessChange
  ├─ Complete-ClosureGitStep → Complete-HarnessGitCommit
  │    插件仓库保存实现提交，记录其提交号
  ├─ 整理收束回执和相关证据
  ├─ openspec.change archive
  │    移动 Change 记录并核验归档，阶段变为 archived
  └─ Complete-ClosureGitStep → Complete-HarnessGitCommit
       规范记录仓库执行最后一次提交
       ├─ 此场景：pre-commit 拒绝 → 留在 archived
       └─ 提交成功：记录 RecordCommit → 阶段变为 complete
```

这不是把成功状态凭空拆成几个词。[ChangeClosure.psm1](D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/ChangeClosure.psm1) 里确实先保存 `archived`，再尝试最终提交；只有后者成功，才保存 `complete`。其关键逻辑可忠实简化为：

```powershell
# 摘自 Close-HarnessChange，省略最终候选内容的构建和校验。
if ($state.stage -eq 'archived') {
    Complete-ClosureGitStep $state $state.recordStep
    # 上面失败会抛出异常，下面两项就不会被写入。
    $state.recordCommit = $state.recordStep.commit
    $state.stage = 'complete'
    Write-ClosureState $statePath $state
}

# Get-ClosureView 的 Complete 就是从该阶段计算出来的。
Complete = ($State.stage -eq 'complete')
```

因此，“收束没完成”在这里有一个很具体的意思：**缺少最后的规范记录提交，以及由其成功产生的完成证据。** 它不表示已经成功的插件提交消失了。Git 实现也明确保留前面仓库已完成的提交，供原操作恢复；不会因为后面的仓库提交失败就把前面的成功一并回滚。`pre-commit` 是实际创建提交之前执行的检查，这个场景的拒绝发生在规范记录仓库的检查阶段。[GitOperations.psm1](D:/Workspace/AngelscriptProject/.agents/skills/git-operations/scripts/GitOperations.psm1)

队列为什么不能继续，取决于另一个明确的读取路径：`harness.queue.advance` 经 `Invoke-HarnessChangeQueue` 进入 `change_queue.py`，读取当前 Change 的归档身份，再调用 `closure_status.py` 的 `inspect_closure` 检查这次收束。

对于这个有收束日志的 Change，检查首先发现阶段仍是 `archived`，就返回 `recordState=close-pending`，也就是“当前收束还有步骤未完成”。队列推进代码只接受 `recordState=archive-pending`，所以它在把当前队列项标为已归档、选择下一项之前就停止了。[closure_status.py](D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/closure_status.py) · [change_queue.py](D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/change_queue.py)

这里的 `archive-pending` 名称容易误解：在这个队列检查里，它表示“归档记录已满足要求，等待队列确认并移到下一项”。它不是说归档目录还没移动。要得到这个结果，仅把阶段字符串改成 `complete` 也不够：检查还会确认归档回执与该 Change、结束决定一致，`RecordCommit` 存在并且属于当前历史，而且该提交保存的归档文件与磁盘上的归档内容相符。这样下一项才不会跨过一项记录仍未保存完毕的工作。

把本例向前走一步看：如果原收束操作在同一授权范围和已接受内容下成功完成最终提交，返回值就能变为 `Stage=complete`、`Complete=true` 并带上 `RecordCommit`；归档持久化检查也通过后，队列才具备继续的条件。随后仍由 `harness.queue.advance` 实际推进，并遵守已有执行授权范围和暂停状态；最终提交本身不会直接执行下一项。

所以我应当把这次进度报告为：**“插件实现提交成功；Change 记录已移入归档；规范记录的最终提交被 pre-commit 拒绝，当前收束待恢复，队列暂不能推进。”** 给定证据没有说明该 hook 具体拒绝了什么；解释这个停点不需要先猜测拒绝原因，也不能据此判断真实项目当前需要怎样修复。
