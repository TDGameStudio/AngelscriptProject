我按你给出的失败场景和当前代码来解释。这里有两个各自保存历史的 Git 仓库：插件仓库保存实现代码；父仓库保存 OpenSpec 的方案、任务、验证证据和归档记录。父仓库还可以保存一个 `gitlink`，也就是“本项目使用哪个插件提交”的指针，但只有明确选入本次收束的指针才会提交。

| 这次发生的事 | 保存了什么 | 现在的结果 |
| --- | --- | --- |
| 插件实现提交 | 这次选定的插件代码及其版本 | 已成功，代码提交仍然存在 |
| Change 归档移动 | 将活动 Change 的目录移到归档位置，保留方案、任务、证据和关闭结果 | 已发生，磁盘上的位置已改变 |
| 父仓库记录提交 | 将这次归档及明确选中的规范、记录、插件指针等写入父仓库的 Git 历史 | 被 `pre-commit` 检查拒绝，尚未成功 |

这里的“记录”不是一句“我做完了”的聊天总结。例如，收束会生成 `attachments/data/harness-closure.json`，里面关联这次 Change 的身份、已接受的收束决定、实现提交和最终处置。它和归档里的其他文件一起进入父仓库提交后，后续读取者才能从 Git 历史核对这次结果。**把目录移走，只改变了工作区文件；它不会自动产生保存这些变化的 Git 提交。**

同一个 Change 的实际调用关系是：

```text
协调者调用 harness.change.close
  -> Close-HarnessChange                  # 按保存的精确收束请求执行各阶段
     -> Complete-ClosureGitStep           # 保存选定的插件实现：本例成功
     -> openspec.change archive           # 移动 Change，随后校验该归档：本例已到 archived
     -> Complete-ClosureGitStep           # 保存父仓库记录：本例被 pre-commit 拒绝
     -> stage = complete                  # 只有上一项成功才执行；本例尚未到达

队列准备推进当前项
  -> inspect_record -> inspect_closure    # 读取同一 Change 的收束状态和归档证据
     -> close-pending                     # 本例仍有待完成的提交
  -> advance 检查失败                     # 保留当前项，不能越过它开始下一项
```

这不是根据字段名字猜出来的。[收束实现](/D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/ChangeClosure.psm1:386)的关键顺序如下，代码省略了候选内容准备与校验，保留了实际调用及状态更新顺序：

```powershell
if ($state.stage -eq 'archived') {
    # 此前还会核对归档字节和已批准的候选内容。
    Complete-ClosureGitStep $state $state.recordStep
    # 父仓库提交失败会在上面抛错，下面这行就不会执行。
    $state.recordCommit=$state.recordStep.commit; $state.stage='complete'; Write-ClosureState $statePath $state
}
```

返回给调用者的 `Complete` 又明确由 `stage -eq 'complete'` 计算。因此 `Stage=archived、Complete=false` 的意思是“已走到归档阶段，完整收束还没完成”，两者并不矛盾。[字段定义](/D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/ChangeClosure.psm1:104)

队列之所以停住，是因为它需要确认**前一个 Change 的代码与收束记录都已按接受的范围保存**。当前的 [inspect_closure](/D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/closure_status.py:79)遇到尚未 `complete` 的收束会返回 `close-pending`；即使阶段已经是 `complete`，它还会核对父仓库提交中是否确实包含一致的归档文件。检查通过才返回 `archive-pending`，这个名称在这里表示“归档结果已持久保存，等待队列登记并推进”。[队列 advance](/D:/Workspace/AngelscriptProject/.agents/skills/harness/scripts/change_queue.py:301)只接受这个状态。若它仅凭目录存在就继续，队列便会把尚未保存完整记录的工作记成已交付，并把未收完的工作留在前一项。

因此，同一个案例里，最后提交若成功，状态会走到 `complete`，队列才可登记这个结果，再继续原先已授权的范围；最后提交被拒绝，就保留 `archived` 和已有插件提交，等待恢复原来的收束请求。精确重试会核对原决定和已保存内容，跳过已完成的阶段，不重复创建插件提交或重做归档。这里尚不知道 hook 为什么拒绝，不能把“提交被拒绝”推断成某个具体错误，更不能把状态直接改成完成。
