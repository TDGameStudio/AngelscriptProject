## Execution contract

- One node is one independently provable feature group. Related positive/negative/boundary cases observe RED together, then implementation, then GREEN together. A missing C++ API gets only a minimal compilable unavailable seam before behavioural RED; compiler errors and crashes are not RED.
- Every command below assumes the current PowerShell 7 Harness context. Build after C++ changes and before each proving binary; only the coordinator schedules UE operations, with source writers paused during build and Automation. Direct-bytecode VM fixtures never invoke Builder or source compilation. Source execution groups 5.1-5.5 and follow-ups 10.1-10.5/11.2 explicitly use the current Builder plus the new emitter; no legacy module/compiler/runtime/test pool or future unified-framework dependency is permitted.
- `Files` basename globs mean only the named maintained SDK or replacement-test files with .h/.cpp extensions, not recursive packages. No Legacy/, Cache/, Standalone, generated bindings or host project edits are included. Historical 5.4 owns its named constructor files; follow-up 10.3 additionally owns the exact canonical host-signature/default/reference/constructor facts listed on its Files line. Other frontend/parser changes require a demonstrated ownership update. Shared files serialize mutation even if graph prerequisites allow concurrency. Graph readiness is not write permission on overlapping metadata/emitter files; coordinate those writers. Detached fixture 1.3 is required before 2.1; all execution paths remain consumers of the same definitions and image APIs.
- Select the listed exact prefix by default. Compatible Ready groups may share the existing `Angelscript.UnitTest.NativeEngine.VM` prefix or a justified NativeEngine regression; record task-specific complete case paths/results and the actual shared command. Do not invent multi-prefix runner parameters. Later dependent code cannot be implemented before prerequisites are proven merely to fill a batch.
- Ordinary failed assertions and local implementation defects are diagnosed, repaired and reverified in the owning group; they do not automatically create a Review or Replan. Replan only when evidence invalidates scope, interfaces, prerequisites, Files ownership or the proof contract. A broad run is evidence only for its exact discovered and executed cases.
- Runtime opcode ownership is explicit in the inventory: 9.1 has 121 integer/scalar rows, 9.2 has 43 floating/conversion rows, and 9.3 has 49 resource/call rows including STR rejection. All 212 supported opcodes need executed paths and independent oracles; reserved/pseudo rejection is separate.
- Each group retains verification evidence on its task card. data/implementation-verification.md and 4.2 remain historical partial-acceptance evidence; 11.3 owns new final acceptance-verification.md after all follow-ups. The Review and acceptance matrix map findings to tasks but never replace task state. Task assignment does not close a finding; no automatic new Review is introduced.
