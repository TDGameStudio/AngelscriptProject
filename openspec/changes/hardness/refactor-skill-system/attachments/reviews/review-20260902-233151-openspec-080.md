## Finding 1 — UTF-8 BOM Hides the Current Task Graph Frontmatter

```yaml
severity: Required
status: resolved
dimensions: [correctness, portability, verification]
```

Files and lines:

- `Tools/openspec/src/core/task_plan.rs:369-386`
- `Tools/openspec/tests/task_plan_contract.rs:3-219`

Original observation:

`parse_dependency_source` recognizes frontmatter only when `lines.first()` is exactly `"---"`. `std::fs::read_to_string` preserves a UTF-8 BOM, so a valid current-format file beginning with the byte sequence `EF BB BF` produces a first logical line of `"\u{feff}---"`. The parser silently selects `LegacyAfter`, ignores the valid `task_graph`, and then reports every body node as `missing-after`.

Reproduction and evidence:

1. Initialize a temporary project with the packaged 0.8.0 EXE and create `product/bom-graph`.
2. Write a CRLF `tasks.md` using UTF-8 with BOM. Its decoded text is otherwise canonical:

   ```yaml
   ---
   task_graph:
     version: 1
     depends_on:
       "1.1": []
   ---
   ```

   The body contains `- [ ] 1.1 Work — verify: \`verify\`` and a valid `Files:` field, with no legacy `After:` line.
3. `openspec instructions apply --change product/bom-graph --json` returns process exit 0 but operation state `waiting`, a ready node whose derived `after` is empty, and `taskIssues[0].code = "missing-after"`.
4. `openspec validate product/bom-graph --strict --json` exits 1 and reports `tasks.md:7 missing-after: Legacy task node must declare '> After: none' or dependency ids`.

Impact:

- A semantically valid current record fails based only on a legal UTF-8 encoding marker.
- This is especially relevant to the supported Windows/PowerShell environment: Windows PowerShell 5.1 commonly emits a BOM for explicit UTF-8 output.
- Hardness receives `waiting` and cannot schedule the task even though the graph and body satisfy the documented v1 contract.
- The PowerShell 5.1 package gate does not expose the defect because it never validates a BOM-prefixed current `tasks.md` fixture.

Resolution condition:

- Normalize one optional leading UTF-8 BOM before frontmatter detection while preserving correct source-line diagnostics and CRLF behavior.
- Add parser and packaged-CLI regressions for UTF-8 BOM plus CRLF current frontmatter. They must produce the same naturally ordered nodes, `after`, `ready`, validation result, and instructions state as byte-identical content without a BOM.
- Retain fail-closed behavior for genuinely malformed or unterminated frontmatter.

## Finding 2 — Explicit YAML String Tags Bypass the Quoted-ID Contract

```yaml
severity: Required
status: resolved
dimensions: [correctness, readability, verification]
```

Files and lines:

- `Tools/openspec/src/core/task_plan.rs:389-460`
- `Tools/openspec/tests/task_plan_contract.rs:151-219`

Original observation:

The current contract requires every `depends_on` key and dependency ID to be quoted. The implementation first deserializes YAML into `serde_yaml::Value`, then `task_graph_has_non_string_ids` checks only the decoded value kind. Lexical quote style is already lost at that point. Consequently an unquoted explicit string such as `!!str 1.1` is accepted as a string, even though it violates the required canonical syntax. The existing negative test covers an ordinary unquoted numeric scalar (`1.1`) but not an explicitly tagged unquoted scalar, anchor, or alias.

Reproduction and evidence:

The packaged 0.8.0 EXE accepted this graph without a diagnostic:

```yaml
---
task_graph:
  version: 1
  depends_on:
    !!str 1.1: []
    !!str 1.2: [!!str 1.1]
---
```

With matching canonical body nodes, `openspec instructions apply --change product/tagged-graph --json` returned `state: ready`, naturally ordered tasks, `after: ["1.1"]`, and `ready: true` for `1.2`. `openspec validate product/tagged-graph --strict --json` exited 0 with `valid: true` and no issues.

Impact:

- Validation does not enforce the exact authoring contract documented by the workflow template, README, architecture, change design, and Task 1.6 acceptance text.
- Multiple lexical spellings can enter current records even though the migration intentionally selected one concise, human-readable, easily audited representation.
- The passing `task_graph_rejects_unsupported_malformed_and_non_string_frontmatter` test overstates coverage: it proves decoded YAML type safety, not mandatory lexical quoting.

Resolution condition:

- Validate the raw frontmatter representation, or use a parser representation that preserves scalar style, so every graph key and dependency occurrence must be a quoted scalar in the accepted grammar.
- Add negative tests for explicit tags and aliases used in place of quoted map keys or dependency entries, alongside the existing plain unquoted-number test.
- Keep both single-quoted and double-quoted stable IDs if both are intentionally part of the contract; document and test the chosen rule explicitly.

## Finding 3 — Current Architecture Documents Contradict the Archive Preflight

```yaml
severity: Advisory
status: resolved
dimensions: [readability, architecture]
```

Files and lines:

- `Tools/openspec/docs/ARCHITECTURE.md:125-136`
- `Tools/openspec/docs/STATE.md:78-84`
- `Tools/openspec/src/cli/objects.rs:706-806`
- `Tools/openspec/docs/commands/change/archive.md:1-13`

Original observation:

`ARCHITECTURE.md` says no task completion gate occurs during `change archive`, and `STATE.md` says archive does not enforce close policy. Production calls `validate_archive_task_policy` before moving the directory, while the canonical command document correctly says archive preflights task closure policy and rejects incomplete completed closures or invalid disposition sets.

Impact:

- Maintainers receive two incompatible descriptions of the OpenSpec/Hardness ownership boundary.
- A future change could remove a required structural safety gate or duplicate it in Hardness based on the wrong document.
- The command documentation is operationally accurate, so this is not an executable release blocker by itself.

Resolution condition:

- Align the maintained architecture/state documents with the implementation: the CLI enforces deterministic structural closure and disposition preconditions, but it does not decide closure kind, verify implementation/reviews, merge specs, or replace the separate post-move `validate --archived` audit.
- Preserve the distinction between a content-preserving directory move and the preflight that authorizes that move.

## Positive Results

- Correctness: graph/body exact key parity, dependencies, cycles, done-dependency safety, mixed syntax, natural ordering, legacy compatibility, and stable JSON all use one shared `TaskPlan` implementation. Malformed frontmatter can no longer masquerade as an empty early plan.
- Readability: `DependencySource`, `TaskGraphFrontmatter`, `is_early_empty`, and the natural comparator make the new boundaries explicit. Templates explain incoming adjacency and keep Markdown order separate from execution semantics.
- Architecture: OpenSpec remains the deterministic parser/validator primitive; it does not add a scheduler, graph database, duplicate Ready store, archive migration, or hidden policy engine. Hardness remains the intended scheduling owner.
- Security: this change adds no network, process-launch, dynamic-library, or new mutation surface. Invalid graph state fails closed for validation and archive authorization. Existing physical path and transactional package controls remain intact.
- Performance: parsing adds one small YAML frontmatter pass and natural ordering over task/dependency lists. The full test suite and CLI self-host checks showed no practical regression; no unbounded new worker, polling, or persistence mechanism was introduced.
- Verification: source/tag/EXE/docs/manifest identity is strongly bound, the Release binary is recorded as byte-reproducible across isolated target directories, and package behavior is exercised in both supported PowerShell hosts. The two findings identify missing adversarial fixtures rather than broad absence of coverage.
