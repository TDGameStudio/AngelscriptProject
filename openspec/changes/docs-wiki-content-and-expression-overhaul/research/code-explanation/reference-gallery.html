CODE EXPLANATION / REFERENCE GALLERY

不拆开源码，解释还能放在哪里？

10 个真实参考的截图研究。目标不是找到一个可直接复制的模板，而是拆出适合 AngelScript 与 C++ 的定位、连接、主次和交互语法。

本轮判断

源码保持连续；短注解常驻；完整解释按需出现；连接线只负责定位，不成为画面主角。

01Tufte 的边注主次：解释靠近，但主动后退。
02GitHub 的范围语义：单行和连续多行共用模型。
03Quarto 的双端匹配：编号与激活范围彼此确认。
04ExplainShell 的细连接：小端口、短路径、低对比。

01 端口与状态线

REFERENCE 01

Unreal Directive · Enhanced Input

以 Blueprint 端口、执行线和数据线建立强方向感，是本轮“连接层级”的视觉上限。

值得保留

  • 端口足够小，却能立即说明信号从哪里进入或离开。
  • 线宽、颜色和汇合关系可在不增加文字的情况下表达状态。

不能照搬

  • 大型节点和高对比连线会压过源码，不能直接移植为源码注解。
09–13 的采纳结论

采纳端口尺寸、线宽和颜色层级；注解端口会更小、连接线更淡，不使用 Blueprint 节点卡片。

02 细正交连接

REFERENCE 02

ExplainShell

保持命令文本连续，再由细线把每个参数接到独立解释，是与本轮最接近的物理连接参考。

值得保留

  • 源命令没有被解释卡拆散，片段仍保持原始顺序。
  • 小圆端点和低对比正交线能表达跨距离、多对多关系。

不能照搬

  • 解释一多就容易形成电路板式噪声，固定宽度布局也不适合直接缩到手机。
09–13 的采纳结论

09、11 使用更短的 CSS 折线；10、12 使用 SVG。静止状态降低对比度，只在关联项激活时增强。

03 纵向对齐双栏

REFERENCE 03

Backbone.js Annotated Source

经典 annotated source 把解说和源码长期并排，优点和本轮要避免的问题都非常明确。

值得保留

  • 解释默认全部可见，适合连续阅读一个完整库。
  • 长段落和长代码块能通过纵向位置建立可靠对应。

不能照搬

  • 50/50 双栏会压缩源码，解释与源码成为两个竞争主体。
09–13 的采纳结论

只保留“纵向接近”原则，不保留固定对半双栏；侧轨最多只是一条窄边注区。

04 单行与多行范围

REFERENCE 04

GitHub Pull Request Comments

成熟的 gutter 入口和连续行范围选择，为源码注解提供了最清楚的定位语义。

值得保留

  • 单行与连续多行共用一套选择模型，范围边界容易理解。
  • 评论入口藏在行号附近，默认不会污染源码字符。

不能照搬

  • 展开评论卡会插入 diff 流并推动后续源码，破坏稳定行几何。
09–13 的采纳结论

采纳行号外缘入口和范围语义；详情改成覆盖式浮层，绝不插入源码行之间。

05 双端编号匹配

REFERENCE 05

Quarto Code Annotations

代码侧编号和解释编号互相匹配，点击后才突出对应行，静止状态十分克制。

值得保留

  • 源码保持连续，编号本身足以维持稳定映射。
  • 点击解释时才突出单行或多行范围，默认页面噪声低。

不能照搬

  • 解释统一放在代码下方时，长代码会产生明显的视线往返。
09–13 的采纳结论

所有实验使用稳定短编号，并在 hover、focus 或 pinned 时同步增强源范围、端口、线和注解。

06 低对比边注

REFERENCE 06

Tufte CSS Sidenotes

最成熟的“主阅读流不动、辅助信息留在页边”方案，直接影响本轮注解的视觉主次。

值得保留

  • 边注靠近引用点，又通过字号、行宽和颜色主动退到第二层。
  • 主阅读流稳定，读者不必跳到页底再寻找脚注。

不能照搬

  • 其窄屏策略会把边注折回正文或切换显示，与本轮锁定的横向画布不同。
09–13 的采纳结论

采纳 margin note 的密度和低对比层级；窄屏仍按本轮约束在组件内部横向滚动。

07 轻标记与按需详情

REFERENCE 07

Material for MkDocs Code Annotations

小型 marker 常驻，完整富文本解释通过点击或聚焦出现，信息密度控制得很好。

值得保留

  • 默认只留下很小的标记，细节不会持续抢占页面。
  • 点击、触摸和键盘都能进入完整解释，交互路径成熟。

不能照搬

  • 作者语法常把编号写进源码注释，本轮不能让演示标记进入真实源码。
09–13 的采纳结论

采纳“短摘要常驻、详情按需出现”；marker 和 details 均放在源码容器外。

08 代码脚注

REFERENCE 08

Code Hike Footnotes

双端编号让源码和解释保持稳定映射，同时复制代码时不会混入脚注内容。

值得保留

  • 源码保持完整，编号不会改变源字符。
  • 解释默认可扫描，适合教程和逐段讲解。

不能照搬

  • 所有解释都放在代码下方，局部注解失去“就在附近”的感觉。
09–13 的采纳结论

采纳稳定的双端标识；把短注解移动到源码外缘或窄侧轨，而不是统一下置。

09 行与词元范围

REFERENCE 09

Expressive Code Text Markers

清楚区分整行、连续范围和词元标记，适合作为激活时的局部源范围反馈。

值得保留

  • 行、范围和词元都有一致且克制的视觉语法。
  • 底色和边框不改动代码字符，可作为瞬时阅读辅助。

不能照搬

  • 它擅长标记而非承载完整原理解释，标签过多时仍会重叠。
09–13 的采纳结论

只在关联项激活时显示淡范围底色；解释文本仍留在外部 note 中。

10 语义悬停

REFERENCE 10

Shiki Twoslash

把类型、错误和符号说明绑定到精确语义对象，并在静止时保持界面安静。

值得保留

  • 解释与具体符号精确绑定，读者可按需取用信息。
  • 默认页面几乎不增加噪声，适合高密度源码。

不能照搬

  • 面向 TypeScript；只靠 hover 也不能覆盖触摸和键盘使用者。
09–13 的采纳结论

采纳悬停预览，同时补齐 focus、Enter 固定和 Escape 关闭，确保鼠标不是唯一入口。

窄屏例外

Tufte 等参考通常在手机上把边注折回正文。本轮实验遵循已经确认的约束：390px 下仍保留完整桌面式注解画布，横向滚动只发生在组件内部，页面本身不会横向溢出。这样能验证源码排版在任何视口都不被改写。
