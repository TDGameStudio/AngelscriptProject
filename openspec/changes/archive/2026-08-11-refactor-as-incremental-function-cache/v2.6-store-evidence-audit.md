# V2.6 Store evidence audit

## Purpose

This attachment freezes the evidence boundary between the already-GREEN V2.3/V2.4
Store implementation and the remaining V2.6 work. It exists to prevent repeatedly
re-reading the same Store tests and to keep `tasks.md` a clean checklist.

The authority for this audit is `store-publication-v1.md`, especially its exact
fault-point list, cancellation/commit table, and "Required store and crash
evidence" section. A test is counted only when it reaches the composed production
Store path or directly proves the platform primitive owned by that path. Similar
behavior in an isolated helper is recorded, but does not silently consume a
missing composed/concurrent case.

## Exact named fault-point gap

The frozen contract names twelve deterministic checkpoints:

1. `BeforePackTempWrite`
2. `AfterPackTempFlush`
3. `AfterPackRename`
4. `AfterManifestTempFlush`
5. `AfterManifestRename`
6. `AfterPointerTempsFlush`
7. `BeforePreviousReplace`
8. `AfterPreviousReplace`
9. `BeforeCurrentReplace`
10. `AfterCurrentReplace`
11. `BeforePendingReplace`
12. `AfterPendingReplace`

The current Store exposes injected filesystem calls and cancellation callbacks,
but it does **not** expose these twelve names as one authoritative checkpoint
surface. Existing tests therefore prove many corresponding operations without
being able to prove that every frozen point is reachable exactly once, in order,
or that a simulated process stop at that precise boundary leaves the specified
temp/final/pointer state.

V2.6 will add one narrow production-owned fault-injection interface with the
exact enum above and an optional pointer on the composed publication call. The
normal path supplies null and has no mutable global state. Pack, Manifest, and
pointer helpers receive the same transaction-local interface; they do not infer
points from test-double call counts. An injected stop reports a distinct Store
control-flow error and the correct pre/post-commit state. It deliberately leaves
the on-disk state as a process stop would; a subsequent writer must clean strict
temps, reread roots, and continue.

This seam is intentionally Store-only. It does not enter Pack/Manifest bytes,
Generation identity, engine state, or Runtime settings, and it is not a second
publication implementation.

## Remaining concurrency gap

Two current tests use the word "concurrent" but inject an already-changed root;
they prove rebase classification, not actual writer serialization. The production
namespace-lock test proves lock exclusion, but not two complete publishers.
Pinned-handle and compaction tests prove the lifetime primitives, but do not yet
hold an active production read session while a complete production writer moves
Current.

V2.6 therefore still needs these deterministic compositions:

- two actual publisher threads targeting one production namespace with the same
  prepared generation and different WriterTokens: exactly one commits Current,
  the other returns the fully validated write-free winner no-op, both succeed,
  Current is valid, and no temp/collision residue remains;
- one production pinned read session kept alive while another thread publishes a
  newer Current: the old session remains bound to and validates the old
  generation, while a newly opened session selects the new generation;
- after each injected fault, a new writer reacquires the namespace, performs
  strict stale-temp cleanup/full root reread, and reaches a valid final Current.

These tests belong in new focused Store test files rather than enlarging the
already large TypeSchema or transaction files.

## V2.6 completion rule

V2.6 may be checked only after:

1. all twelve exact checkpoints have state assertions and recovery assertions;
2. the two real-thread compositions above pass without sleeps or timing-only
   correctness assumptions;
3. the complete Store prefix passes;
4. the complete Cache prefix passes; and
5. the new build/test paths and any discovered defects are recorded in
   `verification.md`, `implementation-issues.md`, and `status.md`.

Real multi-process, Editor GUI, PIE, and Development/Shipping launches remain
V6/V7 acceptance. V2.6 proves the shared Store state machine those later paths
must use; it does not claim editor integration.
