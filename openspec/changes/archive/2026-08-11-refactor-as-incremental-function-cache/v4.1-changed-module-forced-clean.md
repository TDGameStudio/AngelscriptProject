# V4.1 changed-module forced-clean packet

Date: 2026-08-10 (Asia/Shanghai)

## Outcome

V4.1 is complete when a changed disk source enters the existing HotReload-owned
file/dependency selection, the existing `FAngelscriptPreprocessor`, and the
existing `FAngelscriptEngine::CompileModules` pipeline under an explicit
forced-clean cache policy. The selected modules must execute the maintained-fork
parser, type/function generation, layout, function compiler and globals stages,
then use the normal ClassGenerator/swap transaction. No Cache V2 function/body
lookup and no legacy `FAngelscriptPrecompiledData` module load may satisfy a
forced-clean request.

This is the clean fallback and semantic oracle for V4.2–V5. It is not a second
frontend, a standalone cache compiler or an alternate HotReload dependency
resolver.

## Compile policy

Add an appendable compile-cache policy to the existing compile request:

```text
Default
  preserve current compatibility behavior and future lifecycle-selected policy

ForceClean
  reject/bypass every persisted execution-artifact lookup
  clear descriptor loaded-from-cache/precompiled hints before assembly
  run the normal authoritative compiler stages
  still permit normal current-process JIT handoff after bytecode compilation
```

The policy is separate from `ECompileType`. `Initial`, `SoftReloadOnly` and
`FullReload` describe activation/reinstancing behavior; `Default` versus
`ForceClean` describes whether persisted compile artifacts may be reused.
Conflating them would make a soft/full HotReload incapable of acting as the
clean-equivalence oracle once V5 adds function reuse.

Every dependency module descriptor cloned by recompile avoidance must also clear
both legacy-precompiled and incremental-cache loaded flags. The policy must be
observable in `FAngelscriptCompilationEvent` and retained by one
`FAngelscriptCompilationContext`/run id so tests and later diagnostics can prove
which path actually ran.

## HotReload ownership

`PerformHotReload` retains all existing responsibilities:

1. merge changed/deleted/previously failed files;
2. select the changed/dependent file closure using the existing import ownership;
3. preprocess the closure through `FAngelscriptPreprocessor` and its configured
   source provider/hooks;
4. cancel live script tests at the established pre-swap boundary;
5. invoke `CompileModules` with `ForceClean` for V4.1;
6. perform normal compile-error rollback, ClassGenerator handoff, module swap,
   reference replacement, test rediscovery and debugger breakpoint refresh.

V4.1 does not persist the newly compiled result yet. V4.2 classifies its complete
semantic records; V4.3 reuses immutable content and publishes the new generation.
V5 may later select a validated incremental mode for changed modules, but the same
HotReload orchestration and the forced-clean mode remain authoritative.

## First RED/GREEN tests

Create `AngelscriptCacheChangedModuleOracleTests.cpp` as a separate Cache test
translation unit.

1. `ChangedDiskSourceUsesHotReloadOwnedForcedCleanPipeline`
   - compile a deterministic disk module normally and execute `Answer()==41`;
   - rewrite only its function body to return `42`;
   - invoke the real private HotReload transaction through a narrowly named test
     friend, not a copied test implementation;
   - observe preprocess, parse and compile-code events;
   - require the compile run to report `ForceClean`, execute `Answer()==42`, and
     leave the active descriptor without legacy/incremental loaded flags.

2. `ForcedCleanCompileClearsIncrementalArtifactHint`
   - preprocess a self-contained module through the normal frontend;
   - seed only its non-owning `bLoadedIncrementalCache` hint;
   - compile it with `ForceClean`;
   - require the normal parse/code stages, a successful result, an executable
     function and a cleared hint.

The first compile RED must fail only because the new compile policy/options/event
surface is absent. GREEN requires the official Development Editor build, the
focused test class, affected compilation-event and HotReload regressions, the
complete Cache prefix, strict OpenSpec validation and both diff checks.

## Non-claims

- no semantic RecordId comparison or publication in V4.1;
- no per-function cache hit in V4.1;
- no new dependency graph replacing HotReload ownership;
- no broad class/import restore claim from the V3.5 narrow cache shape;
- no Editor GUI, PIE or package acceptance before V6/V7.
