# V3.3 production source discovery and module eligibility

Date: 2026-08-10 (Asia/Shanghai)

## Boundary

V3.3 does not add a second filesystem scanner or a text classifier. Production
discovery consumes the same `IAngelscriptSourceProvider`, typed
`FAngelscriptSourceRoot` and `FAngelscriptSource` surface already used by initial
compile and HotReload. It produces the V3.1 direct plan, current observations
for V3.2's one persisted dependency candidate, and deterministic per-module
exact-fast-path eligibility. It does not preprocess, parse, compare declarations
or guess whether a source edit changes a body, signature, class or layout.

```text
FAngelscriptEngine configured roots/provider/options
                         |
                         v
              production source discovery
       FindSources + exact/canonical source bytes
                         |
       +-----------------+------------------+
       |                                    |
       v                                    v
DirectSourceInputs                   current dependency
provider/mount/file/module           observation table
       |                                    |
       v                                    v
BuildDirectSourcePlan           ValidatePersistedDependencyCandidate
       |
       v
per-module exact eligibility
```

## Provider contract

`IAngelscriptSourceProvider` gains two backward-compatible optional seams:

1. `LoadSourceBytes` supplies the directly observable byte authority. The
   built-in disk provider returns exact file bytes. The default adapter converts
   the provider's authoritative `FString` to canonical UTF-8, so existing custom
   providers continue to compile but remain ineligible unless they also declare
   stable provenance.
2. `QuerySourceDescriptor` returns a source-scoped provider kind, canonical
   implementation identity, optional stable instance identity, version and
   relocation-stable configuration, plus generated-source coordinates when the
   provider kind is Generated. The default returns unavailable; no RTTI name,
   object address or registration order becomes identity.

Inline `Memory` sources are self-describing: their typed memory mount, virtual
path and canonical UTF-8 source text form a stable built-in memory-provider
coordinate. A non-memory provider without a descriptor is represented by one
deterministic unidentified External provider. Its observed inventory/content is
still hashed, but missing identity/version/configuration capabilities mark only
modules whose files resolve through that provider ineligible. An aggregate
custom provider may return different stable descriptors for independent backing
providers, allowing an unstable scope not to contaminate another.

Provider content fingerprints are recomputed from the canonically ordered
current inventory assigned to that provider. Provider and mount configuration
fingerprints never contain host absolute roots. The built-in disk descriptor
versions recursive `*.as` discovery, typed roots, filters and exact-byte loading;
project relocation therefore preserves identity while a file addition, deletion,
rename or byte change changes the direct digest.

## Source validation

Before lookup, every discovered source must satisfy all of the following:

- its typed virtual path, source kind, relative path and derived module name
  agree;
- the persisted coordinate is only `{logical mount, relative logical path,
  module name}` and never contains an absolute filename/root;
- directly loaded bytes are valid UTF-8 and contain no embedded NUL;
- the stable ModuleKey is derived from the logical mount, relative path and
  authoritative module name;
- duplicate/ambiguous logical paths and Unicode simple-fold case collisions are
  rejected across the complete discovery result, including sources returned by
  different provider descriptors;
- generated provider rows carry a nonzero generated-source identity and
  configuration fingerprint; non-generated rows carry neither;
- all limits are checked before the direct plan is published.

The result is atomic. A provider read failure, invalid source descriptor,
invalid UTF-8, collision, budget failure or SourceIndex validation error leaves
no plan, observation or module result.

## Hooks and module-local eligibility

Callers may supply stable preprocess-hook descriptors as V3.1 inputs. The two
legacy global multicast hooks are not introspectable: when either is bound,
production discovery emits an explicitly unfingerprinted hook row for every
current module and the existing SourceIndex closure marks those modules
ineligible. No function pointer, delegate handle or listener order is persisted.
A later stable registration surface can replace those anonymous rows without
changing SourceIndex wire identity.

Module eligibility is not a new authority. A producer-side query validates the
current canonical SourceIndex snapshot and invokes the same closure algorithm
already used by decoded persisted SourceIndex records. Module, source-file,
mount, provider and transitive hook reasons therefore have one matching rule.

## Candidate observations

V3.3 resolves each persisted preprocessor input only from the current direct
projection:

| target | current observation |
|---|---|
| `SourceFile` | current raw content hash for the exact SourceFileKey |
| `GeneratedSource` | current raw content hash for the exact GeneratedSourceKey |
| `Provider` | current provider content fingerprint |
| `Hook` | current hook content fingerprint |
| `Module` | canonical aggregate of that module's current source-file keys and raw hashes |
| `None` + Define/Conditional | the exact `preprocessor:<name>` option fingerprint |

An unresolved target or option is omitted from the observation table. V3.2 then
classifies it as `ObservationUnavailable`, which is a normal miss. Corrupt
candidate structure remains a typed validation failure. Producer capture in V4
must use these same observation hash contracts; it may not invent a second
define/include/generated digest domain.

## V3.3 focused evidence required

- Game, Plugin and Memory discovery through an injected production provider;
- deterministic digest/output independent of provider enumeration order;
- add/delete/rename rejection of the old direct candidate;
- cross-provider exact/simple-fold logical-path collision rejection;
- exact built-in disk bytes plus invalid UTF-8/read-failure atomic reset;
- one unidentified provider module ineligible while an unrelated intrinsic
  memory module remains eligible;
- complete and partial current observation plans for file/generated/option/
  provider/hook/module targets;
- complete Cache-prefix regression and strict OpenSpec/diff checks.

V3.3 does not claim warm activation. V3.4 owns fresh-engine module restore and
numeric route rebuilding; V3.5 owns the zero-preprocess/parse/compiler and
no-redundant-generation proof.

## Completed evidence and retained scaling work

The final production-discovery class is `12/12`, the independent observation
class is `2/2`, the existing SourceProvider compatibility prefix is `4/4`, and
the complete Cache prefix is `371/371`; all have zero failures and skips. The
RED/green artifacts and exact paths are retained in `verification.md`, including
IC-291's module-coordinate and budget-taxonomy correction.

Correctness does not erase the known batching concern recorded as IC-292:
per-module eligibility currently reuses the sole matching algorithm but repeats
whole-SourceIndex validation and scratch construction. The result is bounded and
correct, yet a many-module project can do avoidable repeated work. Before the
V6 production lifecycle invokes this planner on every startup, introduce one
validated/prepared batch query with cumulative accounting; V7 must benchmark the
result. This scaling item does not change V3.3 identities or its acceptance
result and may not be solved by duplicating the eligibility rules in discovery.
