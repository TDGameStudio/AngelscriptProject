# V3.2 persisted dependency candidates

Date: 2026-08-10 (Asia/Shanghai)

## Decision

V3.2 uses the existing SourceIndex `PreprocessorInputs` and `Edges` as the one
bounded, disposable historical dependency candidate. It does not add a global
dependency database, candidate-history file or new SourceIndex wire field.

Three possible lookup shapes were reviewed:

1. rerun the preprocessor to rebuild the include graph before lookup — rejected
   because it cannot prove the V3 zero-preprocess warm path;
2. persist a separate unbounded action/dependency index — rejected because it
   creates a second source authority and independent lifetime problem;
3. retain one candidate in Current SourceIndex and compare it with a bounded,
   candidate-scoped table of current observations — selected because it preserves
   the existing SourceIndex graph authority and makes the planner structurally
   unable to invoke the preprocessor.

## Producer boundary

The successful authoritative preprocessor captures:

- effective include/generated/define/conditional input rows;
- resolved include/generated edges and optional semantic ordinals.

The source planner accepts those rows only after preflighting configured count
and canonical-string budgets. It copies V3.1's validated direct projection,
appends the captured rows, delegates all key/reference/order/collision validation
to `FAngelscriptCacheSemanticArchive::CanonicalizeSourceIndex`, and publishes the
complete SourceSnapshot only on success. The caller remains responsible for
capturing actual frontend facts; V3.2 does not imitate preprocessing.

## Lookup boundary

Lookup receives:

- the current validated V3.1 direct plan and Profile;
- one persisted SourceIndex candidate;
- exactly one current observation `{InputKey, EffectiveValueOrContentHash}` for
  every persisted preprocessor input.

The observation set is candidate-scoped and side-effect-free. V3.3 will build it
from raw source, explicit option, provider, hook and generated-source authorities;
V3.2 only validates it and contains no callback capable of invoking preprocessing.

Lookup order is fixed:

```text
preflight all bounded counts
  -> validate current direct plan
  -> validate persisted SourceIndex and recompute its direct digest
  -> direct mismatch: normal miss, compare zero dependency observations
  -> validate unique observation keys/nonzero hashes
  -> missing observation: normal unavailable miss
  -> changed observation: normal dependency mismatch
  -> copy persisted inputs/edges onto current direct projection
  -> canonicalize and require the same complete SourceSnapshot
  -> exact-only output candidate
```

Malformed, corrupt or over-budget data returns a typed validation error and an
empty output. Direct, missing-observation and dependency mismatches return a
successful validation result with an explicit non-exact match status; callers
treat every non-exact status as an ordinary cache miss. No partial SourceIndex is
published.
