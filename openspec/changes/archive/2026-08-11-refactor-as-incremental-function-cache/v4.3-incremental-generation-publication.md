# V4.3 incremental Generation publication packet

Date: 2026-08-10 (Asia/Shanghai)

## Outcome

V4.3 is complete when a clean-compiled current candidate and the previously
selected validated generation can produce one new complete Cache V2 generation
without repacking unchanged semantic records. Only RecordIds classified as new
by V4.2 are placed in newly encoded Packs. Reused RecordIds retain the exact
immutable Pack locations from the validated base Manifest, retired RecordIds are
absent, and the new Manifest contains the complete current SourceIndex and
ModuleSnapshot graph.

Publication continues through the existing Store transaction. The Store writes
the supplied new Packs first, then validates the complete candidate Manifest by
reopening both its retained old Packs and its newly installed Packs. Only after
that whole-generation validation succeeds may Current or PendingColdStart move.
There is no second incremental pointer protocol and no mutation of an old Pack.

## Input authority and production seam

The production preparation entry point consumes two
`FAngelscriptValidatedGeneration` values:

- `BaseGeneration` is the pinned, completely validated Store generation selected
  before authoritative changed-source compilation.
- `CurrentGeneration` is the completely validated clean-compile oracle candidate
  for the now-current source and compile coordinates.

The preparation layer calls the V4.2 semantic comparator itself. It does not
accept a caller-authored reused/new/retired list, because a stale or forged diff
must not be able to select physical locations. The current generation's retained
decoded records already own canonical payload bytes, so the API also does not
accept a second, potentially divergent prepared-record array.

Both public values are rechecked for canonical bounded Manifest shape and V4.2
rebuilds their semantic owner views before any output is retained. Compatibility,
Context and ArtifactProfile mismatches fail as incompatible generations rather
than as source changes. A selected Store read session remains the stronger
authority for old physical Pack existence; the Store's precommit whole-generation
validation is the final physical proof.

No Engine pointer, current numeric FunctionId, native address, module pointer,
preprocessor scratch or compiler object is an input.

## Deterministic preparation algorithm

```text
validated Base generation                         validated Current candidate
          |                                                    |
          +---------------- V4.2 semantic diff ----------------+
                                      |
                        reused / new / retired RecordIds
                                      |
              +-----------------------+----------------------+
              |                                              |
     reused RecordId                                  new RecordId
              |                                              |
 copy exact Location from Base Manifest        copy canonical payload from
                                                Current decoded record
                                                           |
                                            deterministic BuildPacks(new only)
              |                                              |
              +-----------------------+----------------------+
                                      |
                     Current semantic roots + complete index
                                      |
                          encode complete new Manifest
                                      |
                  PublishGeneration(NewPacks only, Manifest)
                                      |
                 reopen old + new Packs; validate full graph
                                      |
                             atomically move pointer
```

The preparation operation is deterministic and atomic:

1. Reset the output before validation.
2. Validate both Manifest values against the caller's read limits.
3. Compute the V4.2 semantic diff internally.
4. For every `NewRecordId`, find the exact current decoded record and copy its
   canonical payload into the deterministic Pack builder. A missing, duplicate or
   inconsistent record fails closed.
5. Build Packs from only that new-record set. Every emitted Pack index entry must
   be one of the expected new RecordIds, and every expected new RecordId must
   appear exactly once.
6. Start from the current candidate's schema/compatibility/context/profile,
   SourceSnapshot, SourceIndex root and sorted ModuleSnapshot roots, but discard
   all of its temporary physical record locations.
7. Walk the current Manifest's complete sorted RecordId set. Copy a reused
   RecordId's exact base location; use a newly built location for a new RecordId;
   reject every ID that belongs to neither set. Never copy retired entries.
8. Validate and encode the complete result Manifest. On any failure, return an
   empty output with a typed error and underlying validation/diff diagnostics.

Physical Pack grouping, compression codec, offset and generation identity of the
clean current candidate are deliberately irrelevant. The candidate's decoded
canonical records are semantic input; its Pack locations are disposable.

## No-op and lifetime rules

When the current candidate is semantically identical to the base:

- all RecordIds are reused;
- no new Pack is produced;
- every location is copied from the base;
- the encoded complete Manifest and GenerationId equal the base generation;
- Store publication returns a write-free already-selected/no-op result.

When a body-only edit changes SourceIndex, one FunctionBody and its owning
ModuleSnapshot, exactly those three new records are written. The unchanged
ModuleInterface, TypeSchema, ModuleState and DebugSidecar keep their old Pack
locations even if they share one old aggregate Pack with retired records. Pack
garbage collection is intentionally separate: the old immutable Pack remains
while any Current/Previous/Pending/read-session root needs it, and later
compaction may repack the reachable subset.

A read session pinned before publication remains valid after Current advances.
Current publication rotates the prior validated Current to Previous according to
the existing Store rules; it never edits or deletes the pinned old generation.

## First TDD evidence

Add an independent `AngelscriptCacheIncrementalGenerationTests.cpp` class.

1. Compile and validate `return 41` and `return 42` candidates. Incremental
   preparation must report four reused, three new and three retired records,
   encode Packs containing exactly the three new IDs, preserve all four reused
   base locations byte-for-byte, and produce a seven-record complete Manifest.
2. Validate the mixed old/new Packs through the sole complete generation reader
   and prove it is semantically identical to the full current clean-compile
   candidate.
3. Prepare an unchanged current candidate with deliberately different temporary
   Pack sharding. The result must contain zero new Packs and reproduce the exact
   base Manifest bytes/GenerationId.
4. Publish a real disk base generation, pin a read session, publish the body-only
   incremental generation while supplying only its new Packs, reopen Current and
   prove the mixed generation validates while the old pinned session still reads
   the old generation.
5. Reject a forged/missing base location and any impossible validated-generation
   shape with a typed error and completely empty prepared output.

The expected RED is the missing incremental-generation production API. GREEN
requires the official Development Editor build, focused class, Pack/Store
regressions, complete Cache prefix, strict OpenSpec validation and parent/plugin
diff checks.

## Non-claims

- V4.3 does not decide which dependent modules must be recompiled; V4.4 owns that
  propagation.
- V4.3 does not widen clean capture to classes, properties, globals or
  initializers; V4.5 proves those mutation families after their capture support
  exists.
- V4.3 does not provide per-function compiler hits; V5 owns the builder/compiler
  hook.
- V4.3 does not restore an entire `FAngelscriptEngine`. Normal process-local
  binding/type/JIT initialization remains mandatory; the cache holds the
  pointer-free script projection.
- V4.3 does not compact or delete retired objects and does not change persisted
  Pack/Manifest wire schemas or hash domains.
