# V6.6 Cache V2 diagnostic schema 3 and offline correlation

## Outcome

Cache V2 now has one stable, pointer-free diagnostic path that can answer three
different questions without instrumenting the compiler again:

1. What immutable module/type/function artifacts did the Runtime publish?
2. Why did selection, validation, restore, publication or routing reject an
   artifact?
3. Does the current Engine function route still describe the exact FunctionBody
   stored in a selected persisted generation?

The Runtime C++ API owns live observation. The standalone Python tool owns
physical Store inspection, semantic generation comparison and cross-process
correlation. Neither diagnostic path participates in selection, validation,
restore, publication or StaticJIT routing.

## Data flow

```text
Frozen successful publication                         Current Engine routes
(pointer-free canonical records)                      (contains transient VM data)
            |                                                     |
            | bounded production record decode                    | copy stable fields only
            v                                                     v
  module / declaration / type /                  FunctionKey + content/profile
  state / function diagnostic DTOs               + VM/Native selection
            \                                                     /
             +---------------- schema 3 JSON --------------------+
                                      |
                                      | --session-report
                                      v
                         Python CacheV2Dump correlator
                                      |
                 +--------------------+--------------------+
                 |                                         |
       persisted Manifest/Pack                    human/JSON mismatch
       exact RecordIds and bodies                 session=... store=...
```

The route copy deliberately removes `asIScriptFunction*`, numeric FunctionId and
any UObject/Engine/service address. Only `ModuleKey`, `FunctionKey`, execution
hash, debug hash, profile, canonical declaration, selected VM/Native route and
the verified-artifact flag cross the diagnostic boundary.

## Schema 3 publication catalog

Each present publication retains the existing generation coordinates:

- compatibility, context, artifact profile and source snapshot;
- transaction/compile/disposition state and source-index RecordId;
- restored-generation identity when applicable;
- total record count and canonical payload bytes.

Each module adds:

- full ModuleKey, canonical module name and ModuleSnapshot RecordId;
- ModuleInterface and ModuleState RecordIds from the decoded ModuleSnapshot;
- Interface ABI, declarations, parameters, metadata, imports and dependencies;
- TypeSchema RecordId plus stable TypeKey, canonical identity, relations,
  layout, properties, method/VFT/behavior slots, reflection and dependencies;
- module-state profile/input hash, globals and initializer identities;
- FunctionBody RecordId plus FunctionKey, execution/debug/profile identity,
  declaration ABI, source/input digests, invocation/codec metadata and actual
  dependencies;
- a typed `decodeFailures` row if diagnostic decoding ever fails. Such failure
  is observable and never causes the debug frontend to silently omit a record.

Opaque execution and initializer bytes are not copied into JSON. They are
represented by codec version and canonical byte count. This keeps status useful
without turning it into a second bytecode transport.

## Decision trace schema 2

Decision events remain bounded by the existing opt-in ring. Event schema 2 adds:

- optional `validation` with numeric and symbolic error, validation class,
  RecordKind, stage and decimal-string byte offset;
- optional human `detail`, truncated to 1024 characters before journal
  retention.

The startup-restore boundary copies the existing typed restore validation and
detail. The extra fields are explanation only; the event cannot weaken or
replace the original failure result.

## Python correlation rules

The Python tool accepts C++ diagnostic schemas 1, 2 and 3. Schema 3 enables the
full rules below; older schemas use only the coordinates they contain.

For each publication and candidate generation it compares, in deterministic
order:

1. compatibility, context, profile and source snapshot;
2. exact stable ModuleKey set;
3. each reported ModuleSnapshot RecordId against the Manifest root;
4. each reported TypeSchema and FunctionBody stable owner against its exact
   persisted RecordId.

For each current route it locates the persisted FunctionBody by full FunctionKey
and compares ModuleKey, ExecutionHash, DebugHash and Profile. A failure is shown
as a named field with both values, for example:

```text
function-route Vm <FunctionKey> verified=true exact=0/1
  <GenerationId> mismatch
    executionHash session=<live hash> store=<persisted hash>
```

Selected `Native` means the sibling StaticJIT provider currently owns execution;
it does not mean Cache V2 persisted native code. The same persisted FunctionBody
identity remains the VM fallback and correlation authority.

## Offline semantic decoding boundary

Supported v1 ModuleInterface records are decoded through their complete physical
payload: declarations, data types, parameters, metadata, slots, imports and
dependencies. Supported v1 TypeSchema records are decoded through relations,
layout inputs/expectation, properties, methods, VFT, behavior slots, enum/
callable/typedef payload, reflection and dependencies. Supported schemas require
end-of-record; a truncated prefix or trailing bytes is a structured error.

This is still not a second Runtime validator. Python validates physical identity,
bounds and supported wire shape. C++ remains authoritative for derived hashes,
current environment ABI/layout, graph ownership, relocation, ClassGenerator and
activation safety. VM execution, initializer and debug formats remain opaque to
the common Python decoder.

## Operational entry points

Capture a session report through the existing C++/Blueprint/console API, then
correlate it with the Store without launching Unreal again:

```powershell
python Plugins/Angelscript/Tools/CacheV2Dump/cache_v2_dump.py <cache-root> `
    --json --session-report Saved/Diagnostics/cache-v2-session.json

python Plugins/Angelscript/Tools/CacheV2Dump/cache_v2_dump.py <cache-root> `
    --session-report Saved/Diagnostics/cache-v2-session.json
```

Other existing debugging operations remain composable:

```powershell
python Plugins/Angelscript/Tools/CacheV2Dump/cache_v2_dump.py <cache-root> `
    --json --diff Previous Current

python Plugins/Angelscript/Tools/CacheV2Dump/cache_v2_dump.py <cache-root> `
    --json --explain <stable-function-key>
```

The tool is strictly read-only. It does not generate, repair, activate, delete or
recover cache state.
