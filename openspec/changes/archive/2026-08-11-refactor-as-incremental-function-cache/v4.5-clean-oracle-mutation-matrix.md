# V4.5 forced-clean oracle mutation matrix

## Purpose

V4.5 proves that the production clean-capture path turns real, successfully
compiled AngelScript changes into the correct Cache V2 semantic changes. It is
not enough to mutate already-serialized fixture values: that would prove the
archive and diff layers again, but would not prove that the compiler-facing
producer observes classes, properties, globals, initializers, source inputs or
debug data.

The oracle for every row is a new isolated `FAngelscriptEngine`, a normal
preprocess/compile, production clean capture, complete Pack/Manifest validation,
and semantic comparison with an independently clean-compiled baseline. No
cached record may be fed back into either oracle compile.

## Coordinates that must remain separate

```text
raw/source closure        SourceIndex RecordId
public declaration ABI    ModuleInterface + declaration SignatureHash
type/property layout      TypeSchema + TypeLayoutHash/PropertyLayoutFingerprint
module storage/init       ModuleState + storage/hard-value/initializer hashes
function lookup identity  StableFunctionKey
function compile input    FunctionSourceDigest + FunctionInputDigest
function execution        Identity.Content.Execution
function debug mapping    DebugSidecar.DebugHash
module assembly           ModuleSnapshot RecordId
```

Every source-byte mutation changes the raw SourceIndex by design. The
interesting assertion is which semantic records beyond SourceIndex change and
which stable coordinates survive. Whitespace/comment-only changes are therefore
not a whole-generation no-op: they may change SourceIndex and line/debug data,
while still reusing declaration, layout, module-state and execution content.

## Production admission required before the matrix can be GREEN

The current first capture vertical admits exactly one disk source, one enum and
one dependency-free global `int` function. V4.5 must widen the production
producer before it can honestly close the matrix:

1. capture all admitted public declarations rather than a hard-coded enum and
   function pair;
2. capture class/struct type schemas and primitive property layout from the
   compiled VM plus preprocessor descriptors; the VM local-property table is
   complete layout authority, while `FAngelscriptClassDesc::Properties` only
   augments matching reflected properties with UE flags/metadata;
3. capture primitive globals, their declaration ABI and storage layout;
4. capture global/module initializer execution units and initialization order;
5. capture every admitted ordinary global function independently; and
6. preserve `NotCacheable` as a typed safe miss for a shape whose stable type,
   dependency or executable encoding is not implemented yet.

A reflected class also creates VM implementation helpers. For example, the
representative `FCachePayload` compile produces
`__StaticType_FCachePayload` and `StaticClass()` in addition to the user's
global/function. These exact helpers are derived from the class reflection
recipe (`StaticClassGlobalVariableName`) and belong to TypeSchema/ClassGenerator
materialization; they are not independent user ModuleState/FunctionBody units.
The producer must classify every raw VM entity as either an authoritative user
declaration or a recognized generated recipe. An unclassified entity makes the
module `NotCacheable` rather than being silently dropped.

This widening does not imply that fresh-Engine restore already consumes every
new shape. Capture/diff completeness and restore/activation completeness are
separate verticals. A generation may be valid and useful as the clean oracle
before V5-V7 can materialize its entire script graph.

## Mutation matrix

| Family | Independent clean mutation | Required stable coordinates | Required changed semantic coordinates | Propagation expectation |
|---|---|---|---|---|
| Unchanged | compile identical source/options in another isolated Engine | every stable key, declaration/layout/state/input/execution/debug hash and every RecordId | none | no dependent wave; incremental publication writes no Pack |
| Body-only | change one function expression without changing its declaration or line layout | module/type/global keys, edited StableFunctionKey, declaration ABI, unaffected FunctionBody/DebugSidecar RecordIds | SourceIndex, edited FunctionBody, ModuleSnapshot; execution hash must change | ordinary callers depending only on declaration ABI remain reusable; explicit FunctionContent consumers recompile |
| Signature | rename or change the parameter/return declaration of one function | unrelated declaration/type/global keys and records | SourceIndex, ModuleInterface, old/new function key/body/debug ownership, ModuleSnapshot | signature/declaration consumers recompile; unrelated modules remain reusable |
| Class/property/layout | add, remove, rename, reorder or change one property type/qualifier | unrelated type/global/function coordinates | SourceIndex, ModuleInterface when declaration/traits change, owning TypeSchema, ModuleSnapshot | ValueLayout/PropertyLayout and declaration consumers recompile according to the two-coordinate ABI/content model |
| Global storage | add, remove, rename or change one global type/traits | unrelated type/function coordinates | SourceIndex, ModuleInterface, ModuleState, ModuleSnapshot | GlobalStorage/declaration consumers recompile; unrelated globals remain stable when their ordinal-independent identity/content is unchanged |
| Initializer | change only one global/module initializer expression | global declaration key and storage fingerprint when type/traits do not change | SourceIndex, ModuleState initializer execution/input hashes, ModuleSnapshot | Initializer/HardValue consumers recompile; declaration-only consumers remain reusable |
| Include/input | keep the owner source text fixed and change one included/generated/preprocessor input, or change the include closure | stable declarations whose compiled declaration is unchanged | SourceIndex and every semantic artifact whose canonical compile input/result changed | only modules/scopes whose persisted source/dependency closure names that input become dirty |
| Compile option | change one canonical compile/preprocessor option under the corresponding current profile/context | logical module/source keys; stable declarations if semantics are unchanged | SourceIndex and FunctionInput/ModuleState records that consume the option; profile change is a selection miss, not an in-profile diff | candidate with a different required profile is rejected before reuse; an in-profile semantic option change invalidates its consumers |
| Debug-only | insert comments/newlines without changing canonical tokens or execution | all declaration/layout/state keys and hashes, FunctionSourceDigest, FunctionInputDigest, execution hash | SourceIndex, DebugSidecar and ModuleSnapshot; the current v1 FunctionBody also changes because it owns the exact DebugSidecar link/debug hash | no declaration/content-dependent module recompile; StaticJIT execution eligibility uses StableFunctionKey + execution/profile/ABI and must not be invalidated by debug bytes alone |

## Debug-sidecar ownership decision

Function execution and debug content are logically separate, but the current v1
wire graph reaches a DebugSidecar through an exact RecordId stored in
FunctionBody and stores the debug hash in `FAngelscriptFunctionArtifactIdentity`.
Consequently a debug-only edit necessarily changes the FunctionBody RecordId
even when its execution bytes are identical. V4.5 records that fact instead of
claiming impossible record reuse.

The executable invariant is narrower and important for the sibling StaticJIT
change: `StableFunctionKey`, declaration ABI, execution hash and compatible
profile remain unchanged. Debug hash/sidecar bytes are not a Native execution
coordinate. A later wire revision may move debug ownership directly into
ModuleSnapshot to reuse the FunctionBody record physically; that optimization
is not required to prove semantic correctness in V4.5.

## Dependency completeness rule

V4.5 does not infer dependencies from source text after compilation. Production
capture must persist the exact typed dependencies observed by the maintained
compiler/bytecode path. A producer may return `NotCacheable` for an unsupported
shape, but it may not emit a cacheable record while silently omitting a
dependency needed to validate layout, storage, hard values, initializer content
or function execution.

Representative mutation tests prove the admitted production forms. They do not
turn a representative primitive fixture into a claim that every AngelScript
type/container/generated function is already cacheable. Widening the admitted
surface remains incremental and fail-closed.

## Test and observation contract

- Put V4.5 mutation tests in a dedicated test translation unit; do not grow the
  TypeSchema monolith.
- Log baseline/current GenerationId, stable owner keys, per-kind reused/new/
  retired RecordIds and the four function coordinates for every function row.
- Compare mixed incremental publication with the complete current clean oracle;
  semantic equivalence is mandatory.
- Use the Python dump only as a read-only testing/debugging/verification aid to
  inspect produced Pack/Manifest/record content. Python does not generate,
  repair, select, activate or restore a generation and tests its own decoder.
- Keep negative unsupported-shape cases typed and atomic: zero promoted records,
  zero partial Manifest and no live-Engine mutation.

## Exit evidence

V4.5 closes only when all matrix families have focused GREEN evidence from real
compiles, complete Cache regression is green, strict OpenSpec validation passes,
and every discovered producer/codec limitation is recorded in
`implementation-issues.md`. Real Editor/PIE/Development/Shipping multi-launch
validation remains the final V6/V7 lifecycle evidence, not a substitute for
this deterministic oracle layer.
