# V5.6 Production Compiler Reuse Closure

Date: 2026-08-11 (Asia/Shanghai)

## Why this correction exists

The V5 component implementation is real: the maintained builder exposes a
pre-compiler restore callback, the Runtime validates `FunctionSourceDigest` and
`FunctionInputDigest`, the private VM codec restores complete execution/debug
state, and isolated tests prove all supported invocation families. The first real
Development unchanged-warm launch nevertheless exposed IC-475: production
`InitialCompile()` attempts only exact whole-Generation restore. After a safe
`ModuleSetMismatch`, `CompileModules()` receives a post-compile capture context but
no selected persisted Generation and installs no builder callbacks. It therefore
compiles every function normally.

V5.6 closes that production connection. It does not weaken exact-start atomicity,
pretend that a normal compile was a cache hit, remove unsupported scripts from the
package, or replace function-level reuse with a module Blob cache.

## Considered approaches

### A. Widen clean capture until every packaged module is cacheable

This can turn the current 9/11 Generation into 11/11 and make exact warm restore
pass. It is still required over time, but it does not solve body edits, added
modules, profile-compatible partial Generations, or any exact-start miss. It is
not the V5.6 solution.

### B. Restore complete unchanged modules and compile changed modules

This is simpler than function reuse, but it makes module source identity the
compiler-reuse boundary and contradicts the accepted `StableFunctionKey` /
`FunctionSourceDigest` contract. It also loses reuse when one body changes in a
large module. It remains a possible conservative fallback, not the target.

### C. Retain a validated Generation through current semantic preparation and
restore at each maintained-builder invocation

This preserves the exact whole-Generation fast path and uses the already-accepted
function identity/VM attachment design when that fast path misses. It requires a
real current-authority preparation boundary, but does not require a second
compiler pass: the existing pipeline already completes declarations and layouts
before `BuildCompileCode()`. This is the selected design.

## Authoritative compile timeline

```text
Open/pin validated Store read session
        |
        +-- exact source + complete admitted module set
        |       -> exact whole-Generation prepare/commit -> done
        |
        `-- safe exact miss
                -> retain read session and GenerationId
                -> authoritative preprocess/source index
                -> BuildParallelParseScripts
                -> BuildGenerateTypes
                -> BuildGenerateFunctions
                -> BuildLayoutClasses
                -> BuildLayoutFunctions
                -> prepare immutable current module authority
                -> validate matching persisted ModuleSnapshot graph
                -> install builder restore/result callbacks
                -> BuildCompileCode
                       +-- source/input match -> attach cached VM artifact
                       `-- miss/reject/not-cacheable -> compile normally
                -> globals/ClassGenerator/reinstancing/swap
                -> clean-capture the complete successful active candidate
                -> publish one atomic new Generation
```

The read session owns the decoded Generation, cumulative Store-read budget and
pinned Pack/Manifest handles. It must outlive every callback and be destroyed only
after `CompileModules()` no longer refers to its graphs. A rejected/corrupt Store
candidate is never retained for hybrid reuse.

## New production boundaries

### `FAngelscriptCacheCompileReuseContext`

A Runtime Cache-owned transaction object, not an Engine-global singleton. It
owns:

- the one selected `FAngelscriptCacheReadSession`;
- the selected GenerationId/Profile and canonical compile options;
- graph-validation and VM-attachment budgets;
- stable ModuleKey to validated candidate-graph state;
- per-run typed counters and bounded per-function decisions.

`InitialCompile()` receives this context only when Store selection succeeded and
exact restore returned a safe miss with zero active mutation. It passes the
context beside `FAngelscriptCacheCompileCaptureContext`; the two have different
responsibilities. Capture describes the current successful output. Reuse owns the
old immutable input candidate.

### `FAngelscriptCacheCurrentModuleAuthority`

After `BuildLayoutFunctions()` and before `BuildCompileCode()`, Runtime freezes
the current module's pointer-free semantic input authority:

- stable ModuleKey and canonical module name;
- current `ModuleInterface` declarations and ABI;
- current `TypeSchema` layout/property/method/VFT/behavior coordinates;
- current `ModuleState` global/storage/hard-value/initializer coordinates that
  are available before function compilation;
- stable FunctionKey mapping for the builder-created current functions;
- current function-content entries learned as earlier invocations restore or
  compile.

The producer must be shared with Clean Capture rather than become a second
hand-written identity algorithm. Existing capture verticals are split into an
authority-planning phase and an artifact-finalization phase. Authority preparation
may return `NotCacheable`; that module then compiles normally and remains eligible
for the existing post-compile capture decision.

For a persisted `FunctionContent` dependency whose current target content has not
yet been established, lookup returns typed `DependencyMissing` and compiles the
caller. It must never assume persisted content is current merely because the
target StableFunctionKey still exists. This is conservative and correct; later
compiler-result callbacks make the content available to subsequent invocations.

### Callback adapter

The module callback user-data points at stable per-module state owned by the
compile-reuse context. The restore callback:

1. derives the current full-width StableFunctionKey from ModuleKey plus the
   maintained invocation/function metadata;
2. invokes `TryRestoreFunctionFromValidatedGraph()` with the current authority;
3. records one typed decision without numeric FunctionId or pointer identity;
4. on a restored hit, publishes the current execution content into the in-run
   authority map for later function-content dependencies.

The compile-result callback records whether the compiler actually ran and, after
a successful miss, captures the current execution content needed by later
invocations. Post-compile Clean Capture remains the sole producer of persisted
FunctionBody/DebugSidecar records; the callback does not write the Store.

Callbacks are installed only after graph and current-authority preparation
succeed, and only for the module they describe. They are cleared or die with the
builder before their user-data is released.

## Atomicity and failure policy

- Exact whole-Generation prepare/commit remains the fastest path and remains all
  or nothing.
- Hybrid function attachment mutates only the staging script modules already
  owned by normal compilation; it never publishes ActiveModules or routes early.
- A function miss, unsupported invocation or absent authority compiles normally.
- A corrupt function artifact returns `RejectedCorrupt`, leaves that target
  function unmodified and compiles normally. The corrupt candidate is observable
  but cannot become a new publication by reuse alone.
- Any later module/compiler/ClassGenerator/reinstancing failure follows the
  existing all-module no-swap/last-good policy. No partial Current publication is
  produced.
- The final successful publication is rebuilt from the complete active candidate,
  mixing newly encoded records with content-addressed old records only through the
  existing Generation transaction.

## Diagnostics and package semantics

`restoredFromStore` continues to mean exact whole-Generation activation. A hybrid
compile must not set it to true. V5.6 adds an explicit pointer-free function-reuse
summary to the live diagnostic/session output:

- candidate GenerationId;
- candidate-module count;
- restored function count;
- compiled-miss count;
- not-cacheable count;
- rejected-corrupt count.

The decision trace retains per-function `FunctionLookup` events keyed by stable
ModuleKey/FunctionKey and typed lookup status. A normal-verbosity Clean Capture
skip also copies `CaptureResult.Detail` into its event (the adjacent IC-475
debuggability gap).

Focused automation is intentionally more verbose than production diagnostics.
Each two-Engine reconstruction test may dump the complete bounded event set,
candidate/current Generation and SourceSnapshot identities, stable module/type/
function/property keys, graph-validation result, restored/compiled counts,
published module inventory and externally observed values before assertions. This
test-only freedom is used to localize a failure without widening Shipping logs or
making production cache correctness depend on text output. Test scenarios remain
split by cache surface into separate `Angelscript*.cpp` files.

The packaged unchanged-warm oracle accepts exactly one of two successful modes:

1. exact whole-Generation restore with `restoredFromStore=true`; or
2. hybrid reuse with `restoredFromStore=false`, the selected persisted
   GenerationId present, `restoredFunctionCount > 0`, and typed compiler misses
   accounting for unsupported/noncandidate work.

Accepting hybrid mode is not a weaker assertion: a plain fallback compile has
zero restored functions and still fails.

## Production-fidelity test contract

Cache V2 uses four explicit evidence layers. A lower layer is faster and more
diagnostic, but it never substitutes for an outstanding higher-layer acceptance
boundary.

1. **Component/codec tests** exercise stable keys, semantic records, graph
   validation, Store transactions, invalidation planning and maintained-fork
   compiler hooks in isolation. They prove local contracts and failure atomicity;
   they do not prove Engine startup.
2. **Production-path Full-Engine integration tests** create a real temporary
   project `Script/` tree and a dedicated on-disk Cache V2 root, use the normal
   Game virtual-path identity and disk source provider, then call the production
   `FAngelscriptEngine::InitialCompile()` path. That path performs normal root
   discovery, source scanning, Exact Startup selection, preprocessing, builder/
   compiler work, ClassGenerator/reflection materialization, hybrid reuse and
   Store publication. Cold, edited-warm and unchanged-third launches use three
   independent complete Engine lifetimes; no cache DTO, mock compiler or donor
   Engine replaces those boundaries.
3. **Real Editor/PIE tests** add the actual engine subsystem timing, Editor file
   watcher, hot reload/reinstancing, live UObject/World/PIE state, Current versus
   PendingColdStart and post-PIE promotion. These remain required even when the
   same cache behavior is green in a Full-Engine integration fixture.
4. **Real packaged Development/Shipping multi-launch tests** add Cook/staging,
   packaged configuration, the writable cache namespace, executable process
   restart and Shipping-only policy. V7.6 is the final functional acceptance
   layer; V7.7 then measures performance and diagnostic overhead.

The current `CreateScriptScanFreeFullEngineForTesting` name describes only engine
creation: the wrapper initializes a fully bound Engine without automatically
compiling the host project's unrelated scripts. The Cache production fixtures
then explicitly call the normal `InitialCompile()` method against their physical
test project, so source discovery and the Cache/compile path are production code.
Their deliberate controls are a temporary `GetProjectDir`, an isolated cache-root
override, no unrelated plugin script roots, manual startup timing and deterministic
non-threaded initialization. Those controls make failures reproducible; they do
not mock Cache decisions or function compilation.

Consequently, the class-graph/inheritance RED is authoritative evidence of a
production-core gap: the current pre-compiler authority rejects the two-class
module before function lookup, so every method recompiles. It is not a test-helper
artifact. Conversely, making that fixture GREEN closes only layer 2; V5.6/V7 may
claim final production readiness only after the already-required Editor/PIE and
Development/Shipping layers are also green.
