# Current Fork Defect Analysis

## Purpose

This is the triage index for defects and incomplete contracts found while
implementing the raw AngelScript SDK regression suite. It prevents three
different findings from being conflated:

1. a confirmed defect in the vendored fork;
2. an intentional or inherited compatibility limitation whose desired behavior
   has not yet been selected;
3. a defect in the test fixture or oracle.

`fork-limitations.md` remains the detailed behavioral record and `issues.md`
retains the chronological implementation evidence. This file groups the
production-facing findings by severity, root cause, affected surface, active
regression, and repair direction.

## Classification rules

- **Confirmed defect** requires an observable failure or missing effect plus a
  source path that explains it. A setter returning success is not evidence that
  the corresponding lifecycle works.
- **Compatibility limitation** is current behavior that is internally
  consistent but differs from upstream, selected 2.38 behavior, or ordinary SDK
  expectations. It is not called a defect until the intended fork contract is
  decided.
- **Test defect** is a fixture, lifecycle, formatting, or oracle error. It must
  be repaired and recorded, but it must not be added to the production defect
  count.
- A fixed production defect remains in this index as **Fixed, regression
  retained**. It is removed only if the affected feature is removed.

## Compatibility limitations under active characterization

| ID | Current behavior | Why it is not yet classified as a production defect | Active handling |
| --- | --- | --- | --- |
| AS-FORK-LIMIT-001 | With `asEP_FLOAT_IS_FLOAT64=1`, source or registration spelling `double` is publicly canonicalized as `float` while the context ABI remains 64-bit. | This is internally consistent with the fork's configured public scalar alias, though it differs from ordinary spelling expectations. | Preserve original input spelling, exact canonical reflection, and double-width argument/return accessors together. |
| AS-FORK-LIMIT-002 | Application-function registration requires parameter names; equivalent unnamed declarations return `asINVALID_DECLARATION`. | The grammar is restrictive but deterministic. Whether unnamed application declarations should be supported is an upgrade-policy decision. | Keep named positive registrations and separate enabled rejection evidence; add equivalence coverage if the parser is relaxed. |
| AS-FORK-LIMIT-003 | A non-generic native registration without the fork's `asFunctionCaller` payload can register, but execution reports the fixed missing-caller diagnostic. | The fork deliberately routes native calls through generated caller metadata. The risky part is the delayed runtime failure, but removing the requirement would change the embedding ABI. | Keep caller-backed positives and an enabled missing-caller negative. Revisit registration-time validation separately from caller support. |
| AS-FORK-LIMIT-004 | Script classes use implicit-reference local/parameter syntax; explicit handle spelling is rejected in the exercised raw builder paths. | This is a broad fork language choice and cannot be labeled a defect solely from upstream syntax expectations. | Preserve positive implicit-reference object creation/passing and exact explicit-handle rejection. |
| AS-FORK-LIMIT-005 | Mixin receivers are callable through extension-member syntax but not as ordinary first-parameter free calls. | The current compiler consistently treats the receiver as hidden. Selected 2.38 compatibility may choose a broader rule later. | Keep member positives and free-call negatives as separate products. |

## Promotion rule

When a new test fails, it is added here only after the failure is reproduced and
the ownership boundary is known. A source-level suspicion remains in
`issues.md` until runtime or implementation evidence distinguishes a fork
defect from a test defect. Every production repair must move to its own linked
OpenSpec when it changes vendored runtime semantics; this coverage change keeps
the regression and cross-domain verification evidence.
