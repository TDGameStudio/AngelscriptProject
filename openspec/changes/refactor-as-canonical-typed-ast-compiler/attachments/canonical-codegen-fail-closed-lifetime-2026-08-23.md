# Canonical CodeGen fail-closed publication and deferred destructor resolution (2026-08-23)

## Scope and status

This note records a bounded production-CodeGen repair. It does **not** close
tasks 9.1, 9.5, 9.6, 9.7, 10.4, or review task 13.6. The default compiler
pipeline remains `LEGACY`; the opt-in `CANONICAL` path remains a deliberately
bounded subset until the full Sema/CodeGen/Cache/cutover gates are complete.

The change adds two fail-safe properties:

1. A Canonical AST module containing a namespace is rejected before CodeGen
   allocates or publishes runtime declarations, because the current artifact
   does not yet preserve canonical declaration-to-runtime namespace ownership.
2. A value object's generated destructor is emitted correctly even though
   runtime type behavior tables remain detached until the artifact commits.

## Why the namespace gate was necessary

The following source used to build through the Canonical path while the
runtime could expose the function as root `Entry` instead of `Tools::Entry`:

```angelscript
namespace Tools
{
	int Entry()
	{
		return 41;
	}
}
```

This is fail-open behavior: a successful build reported an executable module
whose observable declaration identity did not match the source. The emitter
has no complete namespace-owner map today, so treating a namespace as supported
would be less safe than a deterministic rejection.

`CanonicalDeclIsSupportedForCodeGen()` now rejects
`asAST_DECL_NAMESPACE` during the pre-allocation traversal. `Generate()` also
keeps a diagnostic-only `failureDetail`, and `asCModule::Build()` surfaces that
detail with the normal CodeGen result and source line. The diagnostic identifies
the declaration kind, opaque id, name, and the missing runtime-publication
contract. Callers continue to branch on the integer error code; the text is
not a control-flow ABI.

The real Build test
`CanonicalNamespaceFunctionBuildsCorrectlyOrFailsClosed` accepts only either:

- a correct future implementation that publishes `Tools::Entry` and not root
  `Entry`; or
- the present deterministic failure with no root-function leak and a diagnostic
  containing `unsupported declaration kind Namespace`.

## Deferred destructor root cause and repair

### Observed failure

The existing real Build test
`CanonicalGeneratedDestructorBuildPublishesCodeGenAndExecutes` compiled and
executed this value-object fixture as `42`, but its generated bytecode did not
contain a `CALL` to the generated `~FValue`:

```angelscript
struct FValue
{
	int Value;
	FValue()
	{
		Value = 41;
	}
}

int F()
{
	FValue Object;
	return Object.Value + 1;
}
```

The failure was stable:

```text
F() must CALL the generated destructor; silent DestroyLiveObjects no-op is a false green
```

### Root cause

Legacy `asCBuilder` installs a class destructor id in `objType->beh.destruct`
while declaring the class, before `asCCompiler` generates any function body.
Canonical CodeGen intentionally deferred all method/constructor/destructor
associations to `asSBytecodeCodeGenArtifact::Commit()` so a later emit failure
can abandon the artifact without leaving a runtime type that references a
removed function.

`asCCanonicalFunctionEmitter::DestroyObject()` still looked only at
`objType->beh.destruct`. During Canonical body emission that value was therefore
always zero for a pending script destructor, so `DestroyLiveObjects()` emitted
no call.

### Chosen repair

The repair does **not** publish the provisional function early. Instead,
`DestroyObject()`:

1. uses `objType->beh.destruct` for a registered native or already-published
   destructor;
2. otherwise resolves one pending destructor from the sealed AST's local
   `asSCodeGenFuncBind` set by object type and `asAST_DECL_DESTRUCTOR` kind;
3. emits `CALL` or `CALLSYS` with that pending function's stable engine id.

An inconsistent sealed graph with more than one selected pending destructor
fails as `asINVALID_DECLARATION` rather than choosing one arbitrarily. Runtime
type behavior tables remain unmodified until a successful `Commit()`, preserving
the existing rollback strategy for type/function/module state.

This is the same staged-authority pattern needed elsewhere in CodeGen: backend
emission consumes sealed semantic/artifact facts, whereas module/engine tables
are the post-success installation surface.

## Follow-up boundaries

- Implement namespace-aware canonical owner and runtime namespace publication
  before accepting namespace declarations in CodeGen.
- Extend the staged lookup model from destructor cleanup to any remaining
  CodeGen paths that incorrectly require a post-commit runtime table during
  pre-commit emission.
- Keep the existing artifact rollback tests as the gate for any change that
  moves provisional state into module or engine tables.
- Do not claim full detached/atomic production installation until every
  declaration kind, lifecycle route, metadata surface, and failure path listed
  by task 13.6 is covered.
