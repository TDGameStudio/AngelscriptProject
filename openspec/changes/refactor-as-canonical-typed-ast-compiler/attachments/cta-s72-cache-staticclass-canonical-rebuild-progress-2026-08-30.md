# CTA-S72 Cache StaticClass Canonical Rebuild Progress — 2026-08-30

## Scope and status

This note records the completed non-Standalone Cache V2 closure for generated
`Class::StaticClass()` helpers and the adjacent regressions exposed by the same
`__generated` authority change. The implementation slice is **verified**. It is
progress evidence for the still-open aggregate OpenSpec tasks; it does not by
itself make CANONICAL the product default or close the full change.

The production-default compiler remains `LEGACY`. The native `asCScriptNode`
tree remains available for syntax/recovery, the explicit LEGACY path,
differential tests, and reference. HIR remains physically absent.

## Problem discovered

Clean Cache V2 capture correctly excludes ClassGenerator-derived VM
`FunctionBody` records. Exact restore therefore has to recreate the generated
`Class::StaticClass()` script-function shell and lower its body from the same
retained, sealed Canonical AST; persisting generated bytecode or hand-authoring
an opcode recipe would make bytecode/runtime layout a durable cache contract and
is rejected.

The initial restore implementation found the exact stable declaration key and a
valid body but rejected it because the sealed declaration had no generated
trait:

```text
kind=8
key=UCacheV2RestoredRootObject::StaticClass()
body=6
traits=0x0
parent=14
```

The runtime Parser/Builder path already recognizes the internal
`__generated` decorator and gives the runtime function
`asTRAIT_GENERATED_FUNCTION`. Canonical Sema currently does not carry the same
source decorator into `asAST_TRAIT_GENERATED`. This is a Sema-authority gap, not
a Cache lookup or stable-key failure. Restore intentionally fails closed rather
than accepting an unauthenticated ordinary user function as a generated helper.

## Implemented closure

- `asCBytecodeCodeGen::GeneratePreparedFunctionBody(...)` provides a focused,
  transactional lowering/install boundary for an authenticated, already
  registered empty function shell.
- The boundary verifies the complete publication, binds the exact declaration,
  current module functions, external host declarations, and current module
  globals, emits from the sealed Canonical AST, resolves type relocations,
  commits generation-local TypeId projections, and replaces
  `ScriptFunctionData` only on success.
- Cache restore now allocates the StaticClass global, creates the generated
  helper shell in the class namespace, authenticates its stable declaration,
  and calls the focused Canonical CodeGen boundary before class-descriptor
  binding.
- Durable identity remains the stable declaration/type/global key. Numeric
  TypeId/FunctionId values, addresses, slots, and runtime pointers are resolved
  only against the target Engine generation and are not persisted as identity.
- Parser method-attribute handling now maps the recognized `__generated`
  decorator directly to `asAST_TRAIT_GENERATED`, and Canonical declaration Sema
  admits that trait. The trait is not inferred from the function name during
  restore.
- The producer regression now authenticates the exact generated StaticClass
  declaration, stable key, body and generated trait before CodeGen.
- The prepared object-dispatch preflight now excludes only generated methods
  that do not yet have a Stage 2 Runtime shell. A source-declared method marked
  `__generated` already owned by Stage 2 remains part of the authenticated
  method inventory.

## Adjacent problem 1 — Packaged Runtime Reload fixture did not enable Cache V2

The first broad Cache rerun left three failures in
`Cache.PackagedRuntimeReload`:

- a code-only edit produced the correct outcome and module name but no stable
  changed-module key;
- the compile-failure fixture had no valid `Current` publication before the
  invalid source was written;
- a structural edit retained the executable last-good generation but had no
  `PendingColdStart` publication.

The shared cause was not production runtime-reload logic. The test fixture
asserted Cache V2 lifecycle publications while inheriting the project default
`bEnableCacheV2=False`. It therefore exercised only provider identity capture,
which correctly captured no Cache V2 generation. `CreateEngine()` now enables
Cache V2 explicitly and assigns a per-test isolated cache root. No runtime
reload algorithm or product default changed.

## Adjacent problem 2 — source-declared generated methods were omitted from the prepared dispatch plan

The first complete Compiler CanonicalAST rerun passed `633/634`. The remaining
test failed before bytecode emission:

```text
PreparedGeneratedNativeNonPodMemberCallDoesNotSequenceReceiverTwice
prepared interface dispatch graph methods mismatch:
FPreparedGeneratedNativeReceiverOwner expected=2 actual=3
```

The AST assertions had already proved that the ordinary native member receiver
appeared once, so this was not double receiver evaluation. Mapping
`__generated` into the sealed trait exposed an over-broad preflight filter: the
prepared dispatch plan omitted every generated method, including the authored
`ReadInner() __generated` method whose exact Runtime shell already existed in
Stage 2. The plan therefore contained only `GetInner` and `SetInner`, while the
live object type correctly contained all three methods.

The preflight now defers a generated method only when it has no exact prepared
Runtime binding. Synthesized accessors still publish later with the Canonical
artifact; source-declared generated methods remain in the Stage 2 method graph.
This keeps the graph equality check strict instead of weakening it.

## Architecture decision

Generated helper bodies are derived artifacts. The authoritative semantic input
is the sealed Canonical AST, and the target Engine supplies fresh runtime shells,
bindings, globals, and generation-local IDs. Cache V2 stores stable,
pointer-free identity and semantic sidecar data; it does not turn diagnostic
dumps, raw bytecode, source-tree nodes, HIR, or numeric runtime IDs into an
execution transport.

`__generated` is a semantic trait, not a blanket statement that a method has no
Stage 2 shell. Publication timing is determined by whether an exact prepared
binding exists. That distinction is required for strict dispatch-graph
authentication and for keeping generated accessors transactional.
