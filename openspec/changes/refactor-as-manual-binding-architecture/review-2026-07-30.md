# Re-review — 2026-07-30

## Verdict

The architectural direction remains sound: explicit module ownership, a move-only `FAngelscriptBind` authoring root, immutable catalog snapshots, explicit engine application, per-node results, and a default-on Legacy compatibility gate solve the global discovery/current-engine/PreviousBind coupling together.

The initial re-review found two source-backed design decisions that could materially change the descriptor model:

1. several production providers derive complete declarations from reflected or enumerated types at runtime;
2. many production providers perform auxiliary registrations that are not AngelScript `Register*` operations.

The user subsequently asked to continue closing the spec. The selected direction is A1 + B1. A deeper source pass refined both choices:

- expansion occurs during catalog snapshot materialization rather than only inside `Registry.Register()`, because aggregate families such as `FString` conversions consume ToString metadata contributed by multiple packages;
- `FAngelscriptTypeDatabase`, the ToString list, and `FAngelscriptBindDatabase` are already engine-owned on the normal path, so their new-path replacements are explicit engine-scoped apply targets rather than process-global bootstrap services.

## Confirmed corrections made by this review

### `Binds.Cache` is not the catalog identity store

`FAngelscriptBindDatabase::Serialize` currently serializes only `Structs` and `Classes`. The cache has a magic/version header, but its records do not contain raw AngelScript function/property IDs, PackageIds, NodeIds, callback-order identity, or a catalog fingerprint.

Therefore this change must regression-test cache creation/loading and preserve its existing reflection-binding meaning. It must not add catalog identity to `Binds.Cache` merely because package ordering becomes deterministic. Catalog generation/fingerprint belongs to the binding registry, apply report, diagnostics, and state dump.

### Draft views do not have final NodeIds

The final NodeId depends on parsed and normalized declaration data, which is available only when `Registry.Register()` validates/freezes the draft. A pre-freeze `FAngelscriptBindNode` therefore carries a draft-local node slot/key plus an owner-generation token. The final NodeId is assigned to the immutable node at freeze time and appears in catalog/apply results.

Parse failures that occur before final identity assignment diagnose PackageId, draft node ordinal/key, source provenance, and original declaration. They do not fabricate a final NodeId.

### Validation levels are policy-derived

`Full`, `Partial`, `SyntaxOnly`, and `Custom` are not arbitrary downgrade switches. The descriptor/callable category determines the strongest valid level:

- typed callables with complete type mapping require `Full`;
- `Partial` is limited to documented adapter/type-mapping gaps and still validates every comparable field;
- `SyntaxOnly` is limited to generic/native-erased call paths with no sound typed comparison;
- `Custom` is limited to explicit custom nodes and their dedicated validator.

A provider cannot select a weaker level to suppress a detectable mismatch.

### Shared frontend ownership follows dependency direction

The maintained AngelScript fork owns engine-independent declaration syntax values and structured syntax diagnostics. The Runtime binding adapter converts those values into plugin-owned descriptor records. Fork code must not depend upward on Runtime `FAngelscript*` binding types, and public/frozen descriptors must not retain `asCScriptNode`, `asCDataType`, resolved engine objects, or registration IDs.

## Closed decision A — snapshot-time descriptor expansion

### Source evidence

Complete declarations are currently assembled from reflected/enumerated type data in production code, including:

- `Bind_AActor.cpp`: reflected actor-class spawn declarations;
- `Bind_UActorComponent.cpp`: reflected component create/get declarations;
- `Bind_Delegates.cpp`: delegate copy/assignment and signature declarations;
- `Bind_UStruct.cpp`: reflected struct copy/assignment/property declarations;
- `Bind_Primitives.cpp`: generated boolean accessor names;
- `Bind_FString.cpp`: declarations generated for a set of numeric/value types.

This contradicts a literal-only rule applied indiscriminately to every migrated callable. The one-token literal rule is still appropriate for ordinary author-written declarations; derived declarations need an explicit, inspectable model rather than a raw `FString` escape hatch.

### Approaches

#### A1. Descriptor expansion before snapshot freeze — selected

A typed expansion descriptor records stable ExpansionId/revision/provenance and declares which explicit input views it consumes. `Registry.Register()` validates and freezes that definition as part of the internal package. While acquiring a catalog snapshot, an engine-independent expansion stage receives the complete enabled catalog plus explicit reflection/bind-database/config input views, materializes ordinary child callable/auxiliary descriptors, then parses, normalizes, validates, assigns final NodeIds, and freezes the snapshot before application.

Benefits:

- preserves descriptor-first inspection and per-child apply reports;
- keeps the ordinary `Method`/`Function`/`Behaviour` API family;
- makes generated output deterministic and testable;
- avoids opaque callbacks and ambient engine access.

Cost:

- requires explicit expansion input/fingerprint rules;
- reflection and bind-database availability must be defined for snapshot materialization;
- source-literal architecture checks must distinguish author-written declarations from derived output.

#### A2. Explicit custom apply nodes

Keep derived declarations inside allowlisted custom nodes that receive the explicit engine/apply context.

Benefits:

- smallest migration surface for existing dynamic providers.

Cost:

- declarations and per-child nodes remain opaque until apply;
- weakens preflight, deterministic identity, diagnostics, and multi-engine replay guarantees;
- risks recreating the old callback architecture under a new name.

#### A3. Leave derived providers on Legacy

Migrate only literal/static providers and retain dynamic providers behind the Legacy adapter.

Benefits:

- lowest immediate implementation cost.

Cost:

- contradicts the agreed all-in-tree migration and legacy-off build;
- prevents mechanical removal of the old binding core.

## Closed decision B — explicit lifetime-classified auxiliary registration

### Source evidence

The production binding callbacks do more than call AngelScript registration APIs. A focused source scan found:

| Pattern | Files |
|---|---:|
| `FAngelscriptType::Register(` | 43 |
| `FToStringHelper::Register` | 33 |
| `RegisterTypeFinder` | 13 |
| `FAngelscriptBindDatabase::Get` | 9 |

For example, `Bind_FVector.cpp` registers AS members and also registers an `FToStringHelper`, an `FAngelscriptType`, and a type finder. Requiring side-effect-free `FAngelscriptBind` construction without relocating these operations would silently drop behavior.

### Approaches

#### B1. Classify by lifetime and represent explicitly — selected

Inventory every non-AS side effect and place it in one of three owned paths:

1. replayable engine-scoped metadata becomes an immutable auxiliary descriptor applied to an explicit engine-owned store;
2. genuine process/module-scoped services, if the full inventory finds any, remain outside Bind construction and use an explicit module-owned bootstrap/registration handle;
3. truly exceptional engine-aware work uses a narrowly allowlisted custom node with stable identity and result reporting.

Package providers remain side-effect-free and may reference stable service/type identities, but they do not mutate global registries while constructing a draft.

The focused source pass classifies the known high-volume paths as engine-scoped:

- `FAngelscriptType::Register`, aliases, type finders, and well-known type slots currently route to the current engine's `FAngelscriptTypeDatabase`, falling back only when no current engine exists;
- `FToStringHelper::Register` currently routes to the current engine's ToString list, whose entries may later cache engine-local `asITypeInfo*`;
- `FAngelscriptBindDatabase::Get` currently routes to the current engine's database, including loaded `Binds.Cache` inputs and generated reflected-bind outputs.

The new path removes ambient access and fallback writes for these operations. Packages carry replayable metadata/factories; each engine receives fresh adapter objects, finder closures, ToString entries, and bind-database contributions through its explicit apply context.

#### B2. Add arbitrary package setup callbacks

Allow each package to execute setup/teardown callbacks around descriptor construction/application.

Benefits:

- mechanically easy.

Cost:

- restores opaque ordering and lifetime coupling;
- makes replay, rollback, and unload behavior difficult to reason about;
- broad callbacks can bypass the new architecture.

#### B3. Keep auxiliary calls inside provider construction

Benefits:

- minimal migration diff.

Cost:

- directly violates side-effect-free package construction;
- repeats process-global mutations when packages are rebuilt or tests use isolated registries;
- prevents deterministic multi-engine/catalog tests.

## Current target after review

The change succeeds only when all of the following are true:

1. all in-tree manual providers have explicit module/package ownership and no static discovery;
2. ordinary author-written callables use a full AS declaration in one non-multiline string token, with no `ASParam` or declaration generation by the fluent API;
3. reflected/type-derived declarations use the approved explicit expansion model rather than raw opaque callbacks;
4. shared AngelScript declaration parsing is engine-independent at the syntax boundary and reused by both registration and catalog preflight;
5. typed compatibility validation cannot be downgraded to hide mismatches;
6. draft views are local cursors, while final semantic NodeIds are assigned only at freeze;
7. package construction is side-effect-free, and every auxiliary registration has explicit lifetime ownership;
8. each engine applies one immutable leased snapshot and stores AS IDs only in per-engine results;
9. external unregistration is blocked while an engine lease retains a package;
10. StaticJIT, documentation, timing, disabled-bind configuration, diagnostics, and state dump consume explicit descriptors/results;
11. `Binds.Cache` keeps its separate reflection-binding contract;
12. all Runtime, GameplayTags, and GAS manual providers build and pass applicable tests with `WITH_ANGELSCRIPT_LEGACY_BINDS=0`, while the default-on compatibility source remains available for downstream users.
