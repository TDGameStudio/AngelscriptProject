认识与开始 · start/index

本章要解决什么

本章把当前仓库 Angelscript 插件的装载边界、Script/ 目录、第一个脚本 Actor、保存后的编译反馈和验证迭代串成一条完整路径。走完这一章，你会有一个能在 Unreal Editor 中放置、并能在 PIE 中验证行为的脚本类，而不需要先理解编译器、绑定或热重载内部。

本章面向本仓库当前的 UE 5.7 独立插件 fork。Hazelight 公共站点的介绍仅用于帮助我们检查“读者第一条路径”是否清楚；它的自定义引擎安装假设不是本项目的本地安装契约。

本章的最终成果，是一个像下面这样、能放进关卡并在 PIE 中验证的脚本类：

class AHelloActor : AActor
{
    UPROPERTY(Category = "Hello")
    FString Message = "Hello from AngelScript";

    UFUNCTION(BlueprintOverride)
    void BeginPlay()
    {
        Print(f"{GetName()}: {Message}");
    }
}

按顺序读完下面三页即可：先 确认环境，再 写出可运行的类，最后 学会看编译反馈和热重载。

阅读顺序建议

  1. 先读 ，弄清插件目录约定、Script/ 布局，以及“哪些是本 fork 的本地契约、哪些只是上游假设”。
  2. 再读 ，写出第一个继承 AActor 的脚本类，并理解 UPROPERTY() / UFUNCTION() 如何改变 Unreal 可见表面。
  3. 最后读 ，学会读编译反馈、在关卡中放置实例、用 PIE 验证，并区分“改函数体”与“改签名/属性”两类热重载。

当前 fork 的协作边界

  • 脚本类可以成为 Blueprint 的父类；Blueprint 负责资产选择、可视节点和设计师覆盖，脚本负责文本逻辑和快速迭代。
  • UPROPERTY() / UFUNCTION() 会改变 Unreal 可见表面；没有这些标记的成员仍可在脚本内部使用。
  • C++ API 是否可调用取决于手工绑定、UHT 生成路径或反射回退，不应从 Hazelight 页面推断本地绑定必然存在。

插件定位与准备边界 · start/plugin-and-boundaries

学完能做什么

读完本页，你会知道：这个 Angelscript 插件在项目里应该放在哪、脚本文件应该写在哪、编辑器如何找到并编译它们，以及在阅读文档时如何区分“本 fork 的本地契约”和“上游 / Hazelight 的安装假设”。这一步不写代码，但决定了后面所有页面能否顺利跑通。

插件在项目中的位置

源码插件目录必须名为 Angelscript，并位于项目的 Plugins/Angelscript/ 下。使用源码引擎或项目已有的 UE 5.7 构建环境生成项目文件、编译 Editor Target，并确认 Angelscript.uplugin 已启用。这个仓库本身已经采用以下布局：

MyProject/
├── MyProject.uproject
├── Plugins/
│   └── Angelscript/
│       ├── Angelscript.uplugin
│       └── Source/
└── Script/
  • **Plugins/Angelscript/**：插件本体（C++ 运行时、绑定、UHT 扩展）。你通常不需要改动这里就能写脚本。
  • **Script/**：位于**项目根目录**，与 .uproject 平级。你写的 .as 脚本放在这里，编辑器加载项目时会一并编译。

一句话记住两者的分工：

插件目录名 Angelscript 与项目根下的 Script/ 是加载约定的一部分。如果脚本类在编辑器里始终不出现，第一件事就是确认这两个目录名和层级没有被改动，而不是去复制 Hazelight 文档里的其它目录名或引擎参数来“绕过”问题。

脚本目录的组织

Script/ 下可以自由建子目录来分类脚本。本仓库把可运行的教学示例放在 Script/Examples/ 与 Script/Game/ 下，例如：

  • Script/Game/Example_Actor.as —— 最小的脚本 Actor 类。
  • Script/Examples/Core/ —— 语言与常用特性的短示例（数组、映射、枚举、函数、委托等）。
  • Script/Examples/Extended/ —— 组合多种特性的进阶示例。

在学习本章与 时，这些示例是最可靠的对照来源：文档里的每段代码都应能在这些文件中找到对应写法。

本地契约 vs 上游假设

本 Wiki 描述的是**当前仓库的 UE 5.7 独立插件 fork**，它与上游 AngelScript、以及 Hazelight 的引擎集成假设并不完全一致。阅读任何文档（包括外部资料）时，用下面这张表判断哪些能直接当作事实：

这是…包含能否当作本项目事实
本 fork 的本地契约Plugins/Angelscript/ + 根目录 Script/ 布局、插件 README.md、Script/Examples/ 示例、自动化测试✅ 可以
上游 / Hazelight 假设自定义引擎发行版、特定引擎安装路径、“某个 C++ API 一定已绑定”的推断❌ 不能直接采信

独立使用者的详细安装边界以插件 README.md 为准。本宿主仓库的机器相关路径来自 AgentConfig.ini；**不要**把个人引擎安装路径写进脚本、文档或 Wiki 页面。

检查清单

在进入下一页之前，确认：

  1. 项目下存在 Plugins/Angelscript/Angelscript.uplugin 且插件已启用。
  2. 项目根目录下存在 Script/ 目录（与 .uproject 平级）。
  3. Editor Target 能在你的 UE 5.7 环境中成功编译并打开项目。

第一个脚本 · start/first-script

学完能做什么

你将写出第一个继承 AActor 的脚本类，逐行理解它每一部分的含义，并分清“只对脚本可见的成员”和“通过 UPROPERTY() / UFUNCTION() 暴露给 Unreal 反射的成员”这条关键边界。

前置条件：已经完成 ，项目下存在可用的 Plugins/Angelscript/ 与根目录 Script/。

创建 HelloActor.as

在项目根目录的 Script/ 下新建 HelloActor.as：

Undefined widget 'angelscript-code'

逐行理解

  • **第 1 行 class AHelloActor : AActor**：声明一个脚本类。类名使用 Unreal 约定的 A 前缀（表示继承自 AActor）；: 表示继承。脚本类可以继承 Blueprint 能继承的同一批引擎类。
  • **第 3–4 行 UPROPERTY(Category = "Hello") FString Message = ...**：UPROPERTY() 让 Message 进入 Unreal 反射，从而能在编辑器 Details 面板里编辑、被 Blueprint 访问。Category 决定它在 Details 里的分组标题。FString 是 Unreal 绑定的字符串类型。
  • **第 6–7 行 UFUNCTION(BlueprintOverride) void BeginPlay()**：BeginPlay() 是引擎在 Actor 进入关卡时调用的事件。因为它来自 C++ 父类，覆盖它需要标记 UFUNCTION(BlueprintOverride)。
  • **第 9 行 Print(f"{GetName()}: {Message}")**：Print() 把文本输出到屏幕与日志；f"..." 是格式化字符串，花括号里的表达式会被求值后插入。

关键边界：脚本可见 vs 反射暴露

这是理解整个插件最重要的一条边界：**普通类成员默认只对脚本可见；只有加了 UPROPERTY() / UFUNCTION() 才会进入 Unreal 反射表面**（编辑器、Blueprint、复制等）。

下面这张表把常见写法对应到“Unreal 能不能看到”：

写法Unreal 是否可见典型用途
int InternalCounter;❌ 仅脚本内部计数、临时状态
UPROPERTY() int Value;✅ Details 可编辑、蓝图可读写需要设计师调、或蓝图访问的数据
void Helper()❌ 仅脚本纯逻辑，热重载快
UFUNCTION() void Foo()✅ 蓝图节点要在蓝图里调用
UFUNCTION(BlueprintOverride) void BeginPlay()✅ 覆盖引擎事件响应生命周期事件

再看一个把这几种写法放在一起的例子：

Undefined widget 'angelscript-code'

上面的形状来自仓库示例 Script/Game/Example_Actor.as。其中：

  • UPROPERTY() 成员会出现在关卡实例的 Details 面板中。
  • default SetReplicates(true); 用 default 语句覆盖父类默认值，等价于在 C++ 构造函数里设置。
  • 没有 UFUNCTION() 的方法只能被脚本调用；因为 Unreal 不需要感知它们，改动这类方法时的热重载也更快（详见下一页）。

现在只需要记住“加不加 UPROPERTY() / UFUNCTION() 决定是否暴露给 Unreal”。完整的属性与函数 specifier（可编辑性、Blueprint 暴露、复制、RPC 等）在 与 中展开。

验证与迭代 · start/verify-and-iterate

学完能做什么

你将学会一个完整的“保存 → 看编译反馈 → 放置 → 验证 → 迭代”闭环：读懂保存脚本后的编译结果、把脚本类放进关卡、在 PIE 中确认行为，并分清“只改函数体”和“改签名/属性”这两类改动在热重载上的差别。

前置条件：已经在 Script/ 下写好 里的 HelloActor.as。

验证闭环

整个迭代过程是一个循环——写、存、看、改，再回到写：

按下面的步骤走一遍：

  1. 启动 Editor 并打开项目。
  2. 保存 HelloActor.as，在输出日志中观察 AngelScript 的编译结果；**先处理所有编译错误**，有错误时类不会更新。
  3. 在 Place Actors 面板或类选择器中搜索 Hello Actor，把它拖进关卡。
  4. 选中该实例，在 Details 面板里修改 Message（这正是 UPROPERTY() 带来的可编辑性）。
  5. 运行 PIE（Play In Editor），确认输出日志或屏幕打印里包含实例名和你设置的消息。
  6. 修改脚本并再次保存，观察热重载行为（见下一节）。

两类改动，两种热重载

保存脚本会触发热重载，但影响面取决于你改了什么：

你改了什么例子热重载代价
只改函数体改一句 Print 文本、调整循环内计算小；重新编译逻辑，实例状态一般保持
改反射签名/属性增删 UPROPERTY()、改 UFUNCTION() 参数、改继承大；结构变化，需重新生成类型并检查实例与蓝图子类

没有 UFUNCTION() 的脚本专有方法，Unreal 不需要感知它们的存在，因此改动这类方法的热重载明显快于改动一个 UFUNCTION() 签名。这也是把纯逻辑写成脚本专有方法的一个实际好处。

想拿一个“会动的例子”验证热重载，可以放置 Script/Examples/Core/Example_MovingObject.as 里的 AExampleMovingObject，在 PIE 运行时修改它的移动逻辑并保存，直接观察行为变化。
